# E365 Workbench 0.1

Локальный инструмент для стандартного распакованного экспорта ELMA365.
Доверенный workspace обязателен. Архив сначала распакуйте штатным elma365pm.

Из корня ELMA Wiki:

```sh
npm ci
node tools/package-workbench.mjs
code --install-extension .local/e365-workbench-0.1.0.vsix
```

Откройте папку экспорта. В Explorer появится дерево сервисов, namespace,
объектов, полей и side-файлов. Для кода поля работают F12, Find All References
и команда «E365: Где используется поле?». Привязки формы разрешаются через
dataNamespace/dataCode в пределах одного пакета. Context и ViewContext
различаются. Неоднозначная цель не выбирается автоматически.

Индекс обновляется после сохранения и командой «E365: Обновить индекс».
Внешние изменения файлов требуют ручного обновления. Читаются JSON и .ts
в appViews/widgets/processor/entities; код не исполняется. Symlink не обходятся.
Лимиты: 25 000 записей, 4 МБ на файл, 64 МБ на индекс.

Проверка runtime запускается только отдельной командой: выберите свой
bin/elma-dev.mjs, корень экспорта и адрес сервера, для которого сохранён кеш типов. Это ProcessExecution с аргументами,
`compile --verify --offline`, без shell и без импорта. Нужен установленный
Node.js, зависимости elma-dev и ранее полученный кеш типов. Workbench
сам не получает credentials и не подключается к серверу.

Диагностика: повреждённый JSON, повторные коды полей, отсутствующая привязка
в найденном приложении. Неразрешённое приложение — предупреждение, а не
доказательство сломанной зависимости. Анализ .ts текстовый: совпадения в
комментариях/строках возможны, динамические ключи не учитываются.
Переименование, миграции, manifest/history, полная модель процессов,
визуальный редактор и MCP-адаптер ещё не реализованы.

Локальные unit/CLI/упаковочные проверки не заменяют испытание Extension Host.
Для отладки: `code --extensionDevelopmentPath=./extensions/e365-workbench examples/e365`.
Исходные скрипты и metadata читаются локально; индекс не отправляется в Wiki.
