# E365 Wiki

Самостоятельный Node.js-сервис с русским интерфейсом. Единственный источник конфигурации — загруженный `.e365`. Каждый файл создаёт отдельный приватный проект: оригинал, безопасно извлечённые части, структурный индекс и отчёт разбора. Вход — по одноразовому ключу из письма; GitHub отключён.

Главная объясняет пользу для сопровождения без обещаний измеренной экономии. Viewer начинается с задачи: **найти поле**, **изменить обработчик**, **подготовить обновление**. Публичная демонстрация полностью синтетическая.

## Карта системы и рецензирование функций

`/flows` показывает целые сценарии: цель, роли, исследование, правила, ветки, результат и источники. Локальный Storybook использует тот же каталог и renderer, добавляя постоянные комментарии, ответы, отклонения и принятие конкретной версии.

```powershell
npm.cmd ci --prefix storybook
npm.cmd run storybook
# http://127.0.0.1:6006/
npm.cmd run check:storybook
npm.cmd run build:storybook
```

Начните с «Система / Вся картина». [Правила каталога](docs/STORYBOOK.md), [исследование и бизнес-рецензия](docs/EXPERIENCE_REVIEW.md). Source/Target помечен как проектируемый контракт; бизнес-сценарии ELMA — синтетические примеры. Запись рецензий доступна на этой машине; удалённая совместная рецензия ещё не реализована.

## Запуск сервиса

Для аналитика доступен `/releases`: выберите загруженный DEV пакет и явную предыдущую базу, пройдите изменения, сохраните решения, подготовьте точный оригинал как кандидат и скачайте приватный пакет передачи. Это локальная рецензия владельца; принятие не разрешает импорт, Target и проверки ELMA не выполняются. [Рабочий процесс](docs/workflows/analyst-release.md), [границы и доказательства](docs/contracts/analyst-releases.md).

Для публичного сайта с лендингом, объяснениями и учебными примерами используйте `npm run build:public` и готовый `vercel.json`. Это отдельная статическая сборка без backend, IDE и личного кабинета. Внутренний сервис запускается в Docker по инструкциям ниже. Подробности: [два варианта развёртывания](docs/PUBLIC_DEPLOYMENT.md).

Нужен Node.js 22+.

```sh
git clone https://github.com/netbka/elma_wiki.git
cd elma_wiki
npm ci
npm start
```

Скопируйте `.env.example` в `.env`, настройте существующего бота входа VK Teams (см. ниже), затем откройте http://127.0.0.1:43171. Войдите по ссылке из VK Teams и загрузите файл в «Мои проекты». Ручное создание пустого портала не требуется. Демонстрация: `/p/showcase/`. Инструкции, примеры API и развёртывания: `/guide`. `npm run dev` включает перезапуск при изменении кода.

CLI создаёт отдельный проект владельца `local` для каждого аргумента:

```sh
npm run import -- ./solution.e365 ./another.e365
```

В production локальный вход отключается. После перезапуска требуется повторный вход; проекты остаются на диске.

## Вход через бота VK Teams

На `/login` одна кнопка открывает выделенного бота Wiki. Отправьте ему любое сообщение и нажмите ссылку в ответе — Wiki откроет «Мои проекты» без логина, кода и копирования. Ссылка пригодна для повторного входа семь дней; сессия также действует семь дней. Не пересылайте ссылку: она предоставляет доступ к вашим проектам.

В приватном `.env` задайте `VK_BOT_AUTH_TOKEN`, `VK_API_BASE`, `PORTAL_EMAIL_DOMAIN`, `VK_BOT_AUTH_NAME` (или `VK_BOT_AUTH_ID`) и `VK_LOGIN_BOT_POLL=1`. Polling включайте только для отдельного бота Wiki; общий бот SvoiBot уже имеет своего потребителя. Запускайте один экземпляр Wiki с polling. SMTP не нужен. `/healthz` показывает состояние polling без содержимого сообщений или секретов.

Бот отвечает только в личном чате корпоративному отправителю из доверенного VK event, без использования текста сообщения как логина. Ссылка подписана токеном выделенного бота с привязкой к origin Wiki и сроку; смена токена отменяет ссылки. Подпись переживает перезапуск. Сессии хранятся в памяти: после перезапуска нажмите прежнюю ссылку снова. Стабильный владелец `vk:` сохраняет доступ к прежним проектам. Курсор polling хранится в приватном `.local/vk-login-cursor.json` и обновляется после успешной отправки; сбой доставки вызывает повтор. При неоднозначном сетевом сбое возможен повтор ответа.

Проверки: `node --test test/vk-links.test.mjs test/vk-auth.test.mjs test/email-auth.test.mjs test/service-config.test.mjs` и `node tools/vk-auth-browser-check.mjs`. Тесты используют синтетические события; Storybook `login--ready`, `login--expired`, `login--unconfigured` использует тот же renderer, что `/login`.

## Дополнительный вход по электронной почте

GitHub отключён на сервере и в интерфейсе, даже если остались старые OAuth-параметры. Пользователь вводит адрес почты, получает одноразовый ключ и вводит его на /login. Ключ и сессия действуют 72 часа. Ключ используется один раз; успешная повторная отправка отменяет предыдущий. После пяти неверных попыток нужен новый ключ. Повторная отправка — не чаще раза в минуту, максимум пять писем на адрес и двадцать с одного сетевого адреса в час. За reverse proxy лимит по сетевому адресу общий для клиентов этого proxy.

Скопируйте .env.example в приватный .env сервиса и заполните:

```dotenv
EMAIL_FROM=sender@example.org
EMAIL_CRED_KEY=YOUR_APP_PASSWORD
SMTP_HOST=smtp.mail.ru
SMTP_PORT=465
SMTP_SSL_TLS=true
IMAP_URL=imap.mail.ru
IMAP_PORT=993
IMAP_SSL_TLS=true
DISABLE_LOCAL_LOGIN=1
```

EMAIL_CRED_KEY — пароль приложения почты, хранится только в .env. IMAP предназначен для получения почты и не используется для отправки ключей. Отправка идёт по SMTP с TLS; параметры Mail.ru описаны в [официальной инструкции](https://help.mail.ru/mail/login/mailer/). Письмо содержит русские HTML и текстовую версии, одноразовый ключ и точный срок действия. SMTP-сервер получает адрес получателя и письмо, без файлов проектов.

Ключи (только хеши), сессии и ограничения запросов хранятся в памяти одного процесса. Перезапуск отменяет ключи и сессии, проекты остаются на диске. Владельцы проектов определяются по нормализованному адресу почты; прежние проекты GitHub автоматически не переносятся.

Локальный вход по умолчанию отключён. Только для локальной разработки можно явно установить DISABLE_LOCAL_LOGIN=0 на loopback. CLI-импорт создаёт проекты владельца local, которые видны именно в этом режиме.

Доставка релиза на Target (`/api/connections`, `/api/releases/:id/delivery`) работает только через именованный адаптер; подключение хранит ссылку без учётных данных. Живой путь — адаптер `bridge`: владелец выдаёт в разделе «Доставка на Target» токен моста (показывается один раз, сервис хранит только хеш), оператор запускает на своей машине `elma-dev bridge --target=<dev|test>` (репозиторий `elma-development`; `elma365pm` и токены ELMA остаются там, сервис исходящих подключений не делает). Мост сам опрашивает `/api/bridge/poll` и выполняет экспорт/импорт. `DELIVERY_TIMEOUT_MS` — предел ожидания операции адаптера (по умолчанию 20 минут). Синтетический адаптер для тестов и Storybook включается только явно: `DELIVERY_SYNTHETIC_ADAPTER=1`. `PROTECTED_TARGET_HOSTS` — список узлов через запятую, доставка на которые запрещена независимо от названия подключения (PROD). См. `docs/contracts/target-deployment.md`.

```sh
npm run setup
npm run doctor
```

setup запрашивает адрес отправителя и скрыто — пароль приложения. Существующий файл не перезаписывается. doctor проверяет настройки и хранилище без раскрытия значений; проверка не отправляет письма и не доказывает доставку. После настройки перезапустите сервис.

## Приватность и хранение

Оригинал может содержать код и служебные значения. Владелец проекта видит его через сервис; оператор хостинга имеет доступ к диску. Сквозного шифрования нет. Данные не отправляются автоматически в GitHub, внешним AI или в телеметрию.

```text
.local/projects/<uuid>/
  project.json                 # владелец, checksum, активная версия индекса
  original.e365                # неизменённые байты загрузки
  objects/<sha256>             # извлечённые байты; имя архива не путь на диске
  revisions/<uuid>/
    data.json                  # структурный индекс и происхождение
    report.json                # непонятные части, причины, parserVersion
    inventory.json             # пути внутри файла, размеры и SHA-256
```

Создание использует временный каталог и атомарный rename. Повторный разбор проверяет checksum, записывает новую неизменяемую ревизию и атомарно переключает активный индекс. Ошибка сохраняет прежний результат. Удаление убирает оригинал и ревизии этого проекта. Резервные копии находятся вне этой операции и управляются оператором.

Хранилище рассчитано на **один процесс**, не на несколько реплик. Резервируйте весь каталог `.local`, ограничивайте права к нему. `.local`, `.env`, архивы и QA-артефакты исключены из Git и Docker build context. В репозитории только код, общие инструкции и синтетические fixtures; `dist/data.json` пуст.

## Парсер и границы

`lib/e365.mjs` проверяет ZIP: максимум 128 МБ загрузки, 64 МБ записи, 512 МБ суммарной распаковки, 25 000 записей. Обход путей, ссылки, шифрование и опасный контейнер отклоняются целиком. Вложенные сервисные ZIP читаются на один уровень.

`lib/project-parser.mjs` читает поддерживаемые сущности независимо. Ошибка JSON или неизвестный сервис не уничтожают соседние поддерживаемые объекты. Отчёт использует статусы `missing`, `malformed`, `unknown`, `unindexed`, `opaque` с путём, причиной, версией парсера и JSON pointer для фрагментов. Все безопасно извлечённые байты остаются приватно доступны. Предпросмотр — только текст до 256 КБ; двоичные данные доступны через оригинал.

Индекс — навигация, не полный семантический анализ и не доказательство готовности к импорту. Поиск функций и обращений текстовый, динамические выражения не разрешаются. Неизвестная схема не означает отсутствие данных.

`code`, `serverVersion`, `solution/isAuthor` показываются с источником `package.json#/…`; неверный тип или отсутствие — «не определено». Флаг `isAuthor` описывает исходную компанию, а не предполагаемую цель импорта. Host, IP и среда не угадываются. Зависимости сохраняются в оригинальном package.json; индекс разрешает структурные цели только внутри этого файла. Другие проекты не опрашиваются.

Прежние порталы остаются доступны владельцам с явной пометкой. Если исходный архив раньше не сохранялся, сервис не обещает его восстановить: загрузите `.e365` отдельным новым проектом.

## API

Нужна сессия владельца. Изменяющие запросы требуют `X-Elma-Wiki-Request: 1` и тот же Origin.

| Метод и путь | Назначение |
|---|---|
| `GET /api/projects` | Только проекты текущего владельца |
| `POST /api/projects?filename=solution.e365` | Бинарный `.e365`, `Content-Type: application/octet-stream`; возвращает новый UUID |
| `GET /api/projects/:id/data` | Индекс |
| `GET /api/projects/:id/report` | Приватный подробный отчёт |
| `GET /api/projects/:id/preview?path=…` | Текст из приватного инвентаря |
| `GET /api/projects/:id/original` | Скачать сохранённый оригинал |
| `POST /api/projects/:id/reparse` | Повторно разобрать оригинал |
| `DELETE /api/projects/:id` | Удалить проект |
| `GET /api/projects/:id/diagnostic-summary` | Версия, классы замечаний и количества, без путей и содержимого |

Диагностическая сводка не отправляется автоматически. Приватные API проверяют владельца независимо от знания UUID.

## Docker и HTTPS

```sh
docker build -t e365-wiki .
docker run -d --name e365-wiki \
  --env-file .env.production \
  -p 127.0.0.1:43171:43171 \
  -v e365-projects:/app/.local e365-wiki
```

Пример `.env.production`, хранится вне Git:

```dotenv
HOST=0.0.0.0
PORT=43171
PUBLIC_BASE_URL=https://wiki.example.org
DISABLE_LOCAL_LOGIN=1
EMAIL_FROM=sender@example.org
EMAIL_CRED_KEY=YOUR_APP_PASSWORD
SMTP_HOST=smtp.mail.ru
SMTP_PORT=465
SMTP_SSL_TLS=true
```

Поставьте HTTPS reverse proxy перед контейнером. Само приложение не выпускает TLS-сертификаты. Production-развёртывание и отправка писем требуют настройки владельцем.

Вариант с готовым `compose.yaml`:

```sh
npm run setup -- --production
npm run doctor -- --production
docker compose --env-file .env.production config --quiet
docker compose --env-file .env.production up -d --build
docker compose ps
```

Production-настройка требует HTTPS-адрес и настройки бота VK Teams или пару EMAIL_FROM / EMAIL_CRED_KEY. Compose отключает локальный вход, слушает только loopback хоста, хранит проекты в volume и проверяет `/healthz` с корректным Host. Proxy на хосте должен передавать исходный Host, совпадающий с `PUBLIC_BASE_URL`. Одновременно запускайте один процесс сервиса. Проверка Compose не доказывает работу контейнера или публичного HTTPS.

Для обновления выполните `git pull --ff-only`, затем повторите `up -d --build`. Перед обновлением резервируйте volume отдельно. `docker compose down` останавливает сервис; не добавляйте `--volumes`, если нужно сохранить проекты. Файлы `.env.*` исключены из Git и Docker context, `.env.example` остаётся общим шаблоном.

## Разработка конфигурации и AI-агенты

[Контракт рабочего процесса разработчика](docs/DEVELOPER_VALUE_WORKFLOW.md) описывает Designer-first, файловый сценарий и командное review. Реализация #8 добавляет экспериментальный browser editor; tutorial, package build и обновление ELMA через Wiki ещё не реализованы.

Карта документации: [docs/INDEX.md](docs/INDEX.md). [STATE.md](docs/STATE.md) перечисляет реализованный viewer/editor и ограничения. [COMPILER_PROFILE.md](docs/COMPILER_PROFILE.md) описывает offline compiler/SDK, explicit host/version и evidence.

Следуйте [AGENTS.md](AGENTS.md). Viewer доступен для чтения; для распознанного WIDGET со строковыми descriptor-скриптами или sidecar `.client.ts/.server.ts` доступна ссылка **Открыть редактор скриптов**. Экспериментальный browser workspace хранит отдельную рабочую копию, не меняя оригинал, descriptor, runtime или history пакета. Начните с пути объекта и его происхождения, прочитайте отчёт, учитывайте зависимые модули и сохраняйте непонятые части.

Редактор использует локальные Monaco и TypeScript workers: autocomplete полей descriptor и объявленных server-функций, hover, inline diagnostics, Problems, отдельное предупреждение lint для динамического кода, точное сравнение с оригиналом, autosave, ручное сохранение и checkpoints/restore. Сборка editor assets выполняется перед `npm start`/`npm run dev` и внутри Docker; для запуска через `node server.mjs` сначала выполните `npm run build:editor`. Никаких CDN-запросов нет.

Без compiler profile типы ограничены primitive-полями snapshot: bound app/process задаёт Context, descriptor — ViewContext. Hidden/EVENT fields фильтруются по стороне, неизвестные типы остаются unknown, внешние Namespace/Global/Application API не разрешаются. В inferred-режиме неаннотированный RPC return остаётся unknown.

Оператор может установить **per-project offline SDK profile**: тогда Monaco использует полный предоставленный SDK, а Check — портированный platform compiler с точно закреплённым TypeScript 5.9.3, ES2018 и researched worker options/wrapping. UI показывает explicit host и platform/TS versions; результат pinned к revision/source hash/profile hash. Нет profile или exact DTS request — выводится reason и ограниченный TypeScript check. Установка, supported versions и evidence: [COMPILER_PROFILE.md](docs/COMPILER_PROFILE.md). Wiki не получает DTS из сети и не читает parent credentials/cache. Evidence предоставляет оператор; synthetic tests не являются live cross-check.

Скрипты не исполняются. **Build, deployment и live verification недоступны**. Ни TypeScript PASS, ни offline compiler PASS не доказывают готовность пакета к импорту или состояние целевой компании.

Workspace scoped по owner/project/object. Запись требует ожидаемую revision: конфликт вкладок возвращает 409 и сохраняет локальный текст для сравнения. Любое изменение или restore снимает Check; изменение SDK/profile также снимает compiler evidence. Сохраняются последние 10 autosave-состояний и до 20 именованных checkpoints. Ограничение каждого скрипта — 256 КБ, поддержанного JSON descriptor — 256 КБ. Check ограничен одним worker на процесс, 15 секундами и 256 МБ heap. Это дополнение к single-process модели хранилища.

API редактора: `GET /api/projects/:id/workspace/:objectId`; `POST` к `/save`, `/check`, `/checkpoint`, `/restore` под этим путём. Все mutations требуют JSON, сессию владельца и существующие same-origin/header protections. Save принимает `{revision,files}`, Check — `{revision}`, Checkpoint — `{revision,label}`, Restore — `{revision,checkpoint}` (id либо `original`). Операции принимают только существующие client.ts/server.ts; generated и неизвестные части не редактируются. Исходники и история находятся только в `.local/projects/<id>/workspaces/<derived-id>/state.json`.

Скриптовый цикл: `.client.ts/.server.ts` → совместимый компилятор → согласованные `descriptor/runtime/history` → проверки → импорт в проверочную компанию → повторный экспорт и проверка формы. Подтверждён конкретный сценарий платформы 2026.7.23 и elma365pm 1.19.0 для установленного решения; обновление авторского экземпляра сопровождалось collision. Структурные рецепты и перенос в production требуют самостоятельного испытания.

Вики содержит 26 русских статей, включая рецепты полей, формы, связей, runtime и VS Code Workbench. Синтетические фрагменты в `examples/e365` не являются пакетом для импорта.

```sh
node tools/workbench.mjs check examples/e365
node tools/workbench.mjs index examples/e365
node tools/package-workbench.mjs
# Установить .local/e365-workbench-0.1.0.vsix в VS Code
```

Workbench не выполняет импорт или код пакета. Структурные проверки и упаковка VSIX проверены локально; это не проверка VS Code Extension Host или сервера ELMA.
