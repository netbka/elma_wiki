# ELMA Wiki: единая карта поведения и Storybook

Главный объект рецензии — законченный деловой сценарий: зачем человек пришёл, кто действует, какие правила применяются, что меняется и как доказать результат. Отдельные элементы интерфейса вторичны.

## Запуск

Из корня elma_wiki:

```powershell
npm.cmd ci --prefix storybook
npm.cmd run storybook
```

Откройте http://127.0.0.1:6006/. Порт фиксирован; занятый порт не освобождается автоматически. Storybook слушает только эту машину. Карта доступна также в сервисе по /flows без записи рецензий.

```powershell
npm.cmd run check:storybook
npm.cmd run build:storybook
npm.cmd run test:storybook:browser
npm.cmd run test:flows:keyboard
```

test:storybook:browser проверяет работающий локальный Storybook. test:flows:keyboard самостоятельно запускает временный локальный сервис и проверяет фокус и клавиатурные переходы общего renderer. Для установленного Chrome задайте BROWSER_CHANNEL=chrome. Статическая сборка в storybook/storybook-static предназначена для чтения: сервер записи рецензий в неё не входит. Продуктовые обсуждения решений уже работают в аутентифицированном общем `/solutions`; они не используют локальные подписи каталога и не являются личным хранилищем пользователя.

## Где находится истина

`storybook/review-manifest.json` — текущая карта возможностей, renderer, stories и обязательных состояний. `web/flows/catalog.js` содержит инженерные сценарии: цель, роли, правила, вопросы исследования, источники, шаги, ветки и ожидаемые доказательства. `web/flows/model.js` исполняет их учебные переходы; `web/flows/render.js` используется и /flows, и Storybook. Продуктовые stories вызывают собственный общий production renderer; разметка не копируется.

После действия или перезапуска сценария фокус переходит на заголовок нового шага, включая завершение. Tab продолжает путь с действий этого шага. При первоначальном открытии фокус автоматически не перемещается.

Код и проверенные контракты определяют реализованное поведение. Каталог объясняет их и ссылается на источники; он не отменяет их. При расхождении зафиксируйте замечание и исправьте каталог либо реализацию с доказательством. Изменение поведения требует обновления сценария и источника в той же задаче.

| Обозначение | Что оно доказывает |
| --- | --- |
| Реализовано в Wiki | Поведение есть в коде/тестах; прохождение здесь синтетическое |
| Рабочий инструмент рецензии | Панель комментариев работает локально; учебные действия внутри сценария отдельно моделируются |
| Проектируемый контракт | Ожидаемое поведение, ещё не доказанное в сервисе |
| Пример ELMA | Учебная логика, требующая сопоставления с конкретной конфигурацией |

Stories не подключаются к ELMA. Показ Verified в модели не доказывает развёртывание. DEV и dev2 — разные серверы. Настоящие архивы, имена клиентов, токены и снимки экранов ELMA не входят в каталог.

## Начальная карта системы

Реализованный путь рецензии по #52: Решение → Изменение → Рассмотрение → Готово. Это промежуточный результат: уточнение #94 требует также слияния, физической сборки, native-проверки и контролируемого выпуска; текущие stories не доказывают реализацию этих возможностей. Полный исходный экспорт, частичные изменения и сверка следующего полного экспорта остаются внутри того же движка. `/solutions` и `managed-workspace--*` используют один `web/managed/render.js`; `/workspaces` остаётся аутентифицированной совместимостью с общим доступом к конфигурациям. Раздельные корни сохраняют identity и не превращают legacy ID в полный Solution snapshot. Начните продуктовую рецензию по стабильной ссылке http://127.0.0.1:6006/?path=/story/managed-workspace--empty, затем пройдите состояния и рабочий интегрированный UI по [текущему workflow](workflows/solutions.md). `solution-visual--*` использует общий renderer захваченного процесса/формы. Состав состояний задаёт manifest, а не число stories в тексте. `test:managed:browser` проверяет настоящий синтетический UI/API и построенные stories; это не независимая рецензия или финальная приёмка владельцем.

1. Отдельный просмотр: файл → изолированный проект → карта/покрытие → исследование. Этот путь не создаёт управляемую базу автоматически.
2. Потребность → наблюдения → неизвестные правила → постановка → критерии приёмки.
3. Прохождение → комментарии/отклонение → исправление → повторная рецензия.
4. Source → снимок → исследование → изменение → проверки → кандидат → Target → read-back (проектируемый контракт).
5. Согласование договора: положительное решение, пропуск дубля, возврат и новая версия.
6. Переписка: связи, флаг, тематика, пустое значение, очистка копии.
7. Рабочая копия: поддерживаемый скрипт → сохранение → TypeScript/offline compiler → diff/контрольная точка → восстановление; конфликт вкладок и снятие актуальности Check.

storybook/review-manifest.json связывает возможности со stories и обязательными состояниями. check:storybook проверяет источники, stories и достижимость всех шагов. Публичный сайт, вход и прежний viewer имеют явные исключения до переноса их renderer; они не объявляются покрытыми этим каталогом. Исключение не распространяется на два публичных фрагмента с общим renderer: учебный поиск поля (`public-field-guide--*`) и блок источников статьи (`public-article-sources--*`: источники указаны, не указаны, некорректные) — их stories используют тот же код, что и статическая сборка, см. [workflows/public-article-sources.md](workflows/public-article-sources.md).

## Рецензия

Порядок и критерии: [EXPERIENCE_REVIEW.md](EXPERIENCE_REVIEW.md), адаптация корпоративного продукта: [ENTERPRISE_REVIEW_RULES.md](ENTERPRISE_REVIEW_RULES.md). Локальное замечание каталога относится к сценарию и текущему шагу; рецензии разных stories одного сценария объединены. Продуктовые замечания принадлежат конкретному изменению решения, сохраняют исходные object/step ссылки и автора при исправленных экспортах; их правила заданы [контрактом shared Solutions](contracts/shared-solutions.md).

При переключении сценариев внутри общей карты сохраняются пройденный шаг и незаписанный текст рецензии до перезагрузки страницы. Переход по действию ставит клавиатурный фокус на заголовок нового шага. Если история рецензий недоступна, запись заблокирована; кнопка обновления позволяет повторить загрузку.

Панель сохраняет комментарии, ответы, отклонения, решения и повторное открытие в .local/storybook/reviews.json. Это приватная история вне Git. Имя — добровольная подпись локального рецензента; это не аутентификация и не назначение бизнес-ролей.

Отклонения и открытые blocker/must запрещают принятие на сервере. Закрытие требует объяснения. Новый комментарий снимает старое принятие до нового решения. Отпечаток включает каталог, модель, renderer, stories, сценарные документы и правила рецензии. После изменения версии старые обсуждения доступны в истории, но принятие не наследуется. Старая вкладка получает конфликт версии; обновление комментариев не переносит её на новую версию. Действия рецензии блокируются до полной перезагрузки сценария.

Принятие сценария не разрешает развёртывание и не заменяет проверку прав, компиляции или фактического состояния Target.

## Добавление функции

Контекстная передача решения включает 17 состояний `solution-handoff--delivery-*`:
недоступный адаптер/Target, подготовка и отдельное подтверждение, выполнение,
завершение без проверки, read-back, расхождение/ошибка чтения, неизвестный исход,
ошибка/блокировка, отмена, устаревшая история, ошибка загрузки, потеря ответа и
интерактивный путь. Они вызывают `web/managed/render.js`, `web/releases/render.js`
и `web/releases/delivery.js`, как настоящий Solution handoff. Проверка:
`npm run test:solution-delivery:storybook`; данные и операции синтетические,
#59/#41 остаётся deferred. Проверка файлов пакета не означает native-приёмку.

Объяснения решения, процесса и шага используют `web/explanations/render.js` и
десять stories `solution-explanation--*`: начало, черновик, сохранённый текст,
устаревший источник, загрузка, ошибка, конфликт, прежняя версия и сравнение
нового черновика и интерактивный путь внутри решения. Данные и сохранение учебные. Реальные объяснения хранятся
при решении в аутентифицированном сервисе, а не в Storybook/Git.
`npm run test:explanations:browser` проверяет интегрированный путь; правила —
[contracts/solution-explanations.md](contracts/solution-explanations.md).

Экран доставки имеет 14 stories `delivery--*`: недоступен, готов к подготовке, подготовлен, выполняется, завершён без проверки, проверен, расхождение, неизвестный результат, ошибка, блокировка, отменённая подготовка, устаревшие доказательства, ошибка загрузки и защищённый Target. Они используют настоящий renderer и ViewModel страницы релиза. Состояния явно учебные; операции в Storybook не запускаются. Реальный локальный сценарий проверяет `test:delivery:browser` с синтетическим стендом.

Приватная рецензия релиза имеет девять stories `release--*`: базовая рецензия, влияние необязательного поля и прав, отсутствующая база, блокировки парсера, кандидат, принятие для передачи выданный пакет, выбор сохранённого снимка и ошибка загрузки снимков. Влияние прав учитывает native `permissionsSettings/`; неизвестный сервис по-прежнему блокирует кандидат. Добавление необязательного поля показано как изменение структуры. Stories используют настоящий `web/releases/render.js` и `model.js`, как `/releases`. Учебные решения не сохраняются. [Процесс аналитика](workflows/analyst-release.md) и [контракт](contracts/analyst-releases.md) определяют локальный handoff; это не доставка в ELMA.

Начните с исследования: потребность, текущее поведение/источник, неизвестные правила, роли/права, данные, исключения, критерии приёмки. Добавьте сценарий и все ветки в каталог, story и manifest. Свяжите их с кодом/контрактом и проверкой. Обновляйте STATE только после фактической реализации.
