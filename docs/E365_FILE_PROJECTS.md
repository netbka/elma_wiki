# E365-first: файл → личный проект → практическая задача

Дата решения: 2026-10-06. Задача: #3.

Текущая граница: это контракт прежнего личного file-viewer/storage, а не основная навигация продукта. Solution -> Change -> Review и shared admission задаёт [Solution-first план](SOLUTION_FIRST_PRODUCT_PLAN.md); личные записи остаются приватными. Исторические описания главной и GitHub OAuth ниже не являются текущим UI/auth контрактом.

Поиск #30 использует `dist/object-search.js`: точные поля/функции ведут к их индексированному описанию и исходному пути, не только к объекту. Query сохраняется при возврате; повторяющаяся ссылка не выбирает первое определение. Структурно неподдержанные объекты объясняют доступный просмотр исходника/оригинала/отчёта. Это не обновляет экспорт или нативную ELMA.

**Статус: реализовано в ветке feat/e365-private-projects. Проверены приватный upload/viewer, original/report/preview, reparse/delete и сохранение индекса при ошибке. GitHub OAuth App требует регистрации владельцем; production-выкладка не выполнялась.**

## 1. Что меняется

ELMA Wiki — помощник разработчика по конкретному экспорту, а не панель управления инфраструктурой и не браузер GitHub-репозиториев.

Единственный источник пользовательского проекта — `.e365`. Одна загрузка создаёт один независимый проект. Имя файла и package.code не являются идентификатором проекта: два одинаково названных файла не объединяются и не перезаписывают друг друга. Несколько приложений/сервисов внутри одного архива остаются частями этого проекта.

Пользователь не создаёт пустой портал, не выбирает окружение, не указывает адрес сервера и не подключает репозиторий. Разбор, сохранение, индекс и настройка viewer выполняются после выбора файла.

GitHub остаётся только способом входа. Удаляются выбор репозитория, repo scope, repository API, импорты каталогов, синхронизация и соответствующие инструкции. OAuth-токен после получения идентификатора пользователя не нужен сессии. Старое согласие на широкие права GitHub не следует считать автоматически отозванным: это отдельная процедура у провайдера.

## 2. Главная: готовый текст и порядок блоков

### Первый экран

**Меньше кликов в ELMA365. Больше времени на разработку.**

Загрузите файл `.e365`. Найдите нужное поле, форму или обработчик и получите понятный маршрут: где находится код, чем его менять и как проверить результат.

Главное действие: **Загрузить E365**.
Второстепенное: **Посмотреть пример** — синтетический проект, без входа и реальных клиентских данных.

Три коротких шага: **Загрузите файл → Выберите задачу → Найдите место изменения и инструкцию**.

Не показывать здесь дерево всех сервисов, статистику по десяткам метрик, JSON, окружения, зависимости, терминальные команды и длинный технический справочник. Не обещать измеренную экономию в часах или процентах без замеров.

### Практические сценарии

**Найти поле и понять, где оно используется.** Вместо переходов между формами — поиск по коду поля, объявлениям и обнаруженным обращениям. Результат: объект, путь, связанный обработчик и границы статического поиска.

**Изменить обработчик без поиска по всему проекту.** Найти форму, клиентскую/серверную функцию и привязку события. Результат: нужный исходник и инструкция по совместимой проверке/компиляции. Наличие функции не означает, что она подключена к событию.

**Подготовить проверяемое обновление.** Разобраться в происхождении решения, согласованности исходников и runtime, истории версий и проверке результата после импорта. Viewer не выполняет публикацию и не хранит токены ELMA.

### Ключевой принцип — отдельный заметный блок на главной

**Один раз создать в конструкторе. Дальше — работать с установленной копией через проверяемые файлы.**

Условная схема, не обнаруженная инфраструктура пользователя:

`Авторская компания → первичная установка на тестовую компанию → файловые итерации и проверка → перенос проверенного пакета в рабочую компанию`.

В проверенном нами сценарии авторский экземпляр решения отклонял файловое обновление форм с конфликтом `collision`. На компании, где решение установлено, последовательные обновления из согласованного пакета прошли проверку повторным экспортом и в Designer.

Важно: **это не означает «поменяйте любой JSON, и сервер обновит себя».** Для проверенного пути нужны согласованные `.client.ts/.server.ts`, `descriptor`, скомпилированный `runtime` и новая запись `history`. Целевая система при импорте не компилировала runtime заново. Проверка только exit code импорта недостаточна.

Подробности, версии, ограничения и инструкция раскрываются по ссылке «Как устроено файловое обновление», а не занимают весь первый экран.

## 3. Что именно подтверждено, а что нет

Внутреннее исследование от 5–6 октября 2026 зафиксировало:

- тестовый round trip формы/виджета на ELMA365 2026.7.23 с elma365pm 1.19.0;
- последовательные небольшие изменения исходника, соответствующий runtime и новые версии history;
- проверку опубликованного состояния и совпадения повторно экспортированных исходников/descriptor/runtime;
- отказ файлового обновления авторского экземпляра в проверенном сценарии;
- использование side-файлов TypeScript при импорте и отсутствие перекомпиляции runtime целевой системой в этих экспериментах.

Эта проверка не доказывает универсальность для всех сборок, сервисов, бизнес-процессов, модулей или режимов обновления. **Перенос в PROD в данном описании — следующий рекомендуемый этап, а не уже выполненный эксперимент.** Нельзя переносить widget-компиляцию на процессный scripts без отдельного контракта.

Различие относится к **конкретному решению в компании**, а не к физическому серверу вообще. Одно окружение может содержать и авторские, и установленные решения.

`package.json#/solution/isAuthor` — полезное свидетельство происхождения экспортированного снимка. Значение `true`/`false` отображается только при наличии настоящего boolean. При отсутствии или другой форме значения — «не определено», с сохранением исходной записи для исследования.

**Флаг в загруженном архиве описывает экспортировавшую компанию на момент выгрузки. Он не доказывает состояние предполагаемой цели импорта.** Нельзя по одному исходному архиву запретить первичную установку на другой сервер или объявить будущую цель готовой к обновлению. Перед файловой итерацией проверяют установленное решение на цели и получают свежий экспорт цели.

Официальный общий маршрут DEV → TEST → PROD описан ELMA в Low-code CI/CD; это следует отделять от нашего экспериментального вывода о файловом обновлении форм:

- https://elma365.com/ru/help/platform/low-code-ci-cd.html
- https://elma365.com/ru/help/platform/upload-solution-file.html
- https://elma365.com/ru/help/platform/update_solution.html

## 4. Экран после входа и viewer

После входа: **Мои проекты** и одна заметная область **Загрузить E365**. Новый проект создаётся после успешного безопасного чтения архива; ошибка не оставляет пустую карточку.

Карточка проекта: исходное имя файла, время загрузки, краткий результат структурного разбора, кнопка «Открыть». Нет обязательных полей сервера, названия проекта и репозитория.

Первый экран проекта отвечает на вопрос **«Что вы хотите сделать?»**: найти поле, изменить обработчик, подготовить обновление. Подсказки используют объекты именно загруженного файла. При отсутствии поддержанных объектов предлагается отчёт разбора, а не фиктивный рабочий сценарий.

Основная навигация ограничена четырьмя разделами:

1. Начать с задачи.
2. Объекты и файлы.
3. Практические инструкции.
4. Не удалось разобрать — со счётчиком и понятным статусом.

Идентификаторы, package metadata, ссылки, JSON, исходники и детализация охвата раскрываются по запросу. Из карточки объекта всегда есть явный путь назад к результатам поиска, из проекта — к «Моим проектам». Работа на мобильном устройстве и с клавиатуры обязательна.

Для каждой инструкции сохраняется шаблон: **задача → инструмент → точное место изменения → пример → проверка результата → ограничения/откат**. Не предлагать пользователю команды ещё не установленного или не опубликованного инструмента без пояснения предварительных условий. Вход в Wiki не должен требовать установки CLI.

## 5. Изоляция и настоящие зависимости

Хранилище и состояние viewer изолированы по ownerId и случайному projectId. Поисковый индекс, выбранный объект и фильтры одного проекта не наследуются другим. Удаление и повторный разбор одного проекта не меняют другие.

Убираются автоматическое объединение по окружению и разрешение поставщиков среди других проектов. Никакой обязательной загрузки соседнего проекта.

При этом **не удалять настоящие зависимости из оригинального package.json**. Это содержимое пользовательского файла. В расширенных сведениях допустимо показать: «В этом пакете объявлена внешняя ссылка; наличие и совместимость цели не проверены». Нельзя выдавать независимость viewer за отсутствие зависимостей у самого приложения.

## 6. Метаданные, а не придуманная инфраструктура

Не подставлять знакомые автору серверы, адреса, IP, проекты и связи между ними. Не восстанавливать топологию из произвольной URL-строки в скрипте.

Каждый вывод о конфигурации сопровождается происхождением: архивный путь + JSON Pointer, например `package.json#/serverVersion` или `package.json#/solution/isAuthor`. Отсутствие поля — «Не найдено в этом файле», а не подстановка значения по умолчанию.

Экспорт может содержать настройки конкретных компонентов и интеграций. Нельзя заранее утверждать, что в нём нет адресов или что он описывает всю инфраструктуру платформы. Неизвестные схемы доступны в оригинале и попадают в отчёт. Значения секретов не включаются в общий индекс или публичную диагностику.

## 7. Неполный разбор — нормальное видимое состояние

Раздел «Не удалось разобрать» обязан различать:

- неизвестный сервис или формат сущности;
- неподдержанное свойство/фрагмент схемы;
- некорректный JSON;
- файл/ресурс, объявленный в manifest, но отсутствующий в архиве;
- непрозрачный контейнер data;
- сохранённые, но не проиндексированные записи.

Для каждой записи: приватный путь и JSON Pointer при наличии, причина, версия интерпретатора, сохранность оригинала и следующее действие. Ошибка одной сущности не должна скрывать прочитанные части. Нельзя отмечать неизвестный сервис как полностью поддержанный только потому, что manifest читается.

Результат разбора описывается как **структурный индекс**, не гарантия готовности к импорту, проверки прав или выполнения бизнес-логики. Для неизвестной структуры нельзя выдавать отсутствие распознанных полей за их реальное отсутствие.

Исключение: опасные архивы по-прежнему отклоняются целиком — обход путей, симлинки, ZIP bombs, превышение лимитов, ZIP encryption и ошибки контейнера. Не ослаблять защиту ради частичного результата. Непрозрачный штатный data сохраняется без попыток расшифровки.

## 8. Сохранение, повторный разбор и конфиденциальность

Сохраняются оригинальные байты .e365, контрольная сумма, безопасный инвентарь записей, структурный индекс, отчёт и версия парсера. Не использовать архивные имена как непосредственные файловые пути хранилища; можно хранить содержимое по хешам с приватным индексом путей.

Это изменение политики относительно текущего main, где сохранялся только индекс. До загрузки объяснить: **оригинал сохраняется для просмотра и повторного разбора, может содержать код/служебные значения и доступен оператору хостинга; другие пользователи его не видят**. Не обещать сквозное шифрование, если оно не реализовано.

Создание проекта и смена активного индекса атомарны. Повторный разбор использует неизменённый оригинал; ошибка нового парсера не уничтожает предыдущий результат. Доступ к индексу, оригиналу, preview, отчёту, повторному разбору и удалению проверяется по владельцу, не только по UUID. Preview выводится как текст, без исполнения HTML/JS и внешних запросов.

Исследовательский материал остаётся приватно привязан к проекту. Никакой автоматической отправки исходников, токенов или бизнес-настроек в GitHub issues/телеметрию/внешний ИИ. Экспорт общего диагностического отчёта по умолчанию содержит только версию парсера, классы ошибок и количества — без имён объектов, путей, значений и исходного кода. Передача выбранного обезличенного фрагмента для исследования — отдельное осознанное действие владельца.

Старые порталы и индексы не удаляются молча. При отсутствии сохранённого оригинала показывается legacy-статус и предложение загрузить .e365 отдельным новым проектом; нельзя обещать восстановить исходники из старого структурного индекса.

## 9. Точки изменения в текущем коде

- `server.mjs`: единая загрузка файла с созданием изолированного проекта; закрыть repository endpoints; все новые raw/report/reparse/delete endpoints под owner-check.
- `lib/auth.mjs`: GitHub identity-only, без repo и сохранения access token в сессии.
- `lib/portals.mjs`, `lib/store.mjs`: атомарное файловое хранилище, оригинал и версии индекса, legacy-переход без потери данных.
- `lib/e365.mjs`: покрытие/происхождение, отказ от межпроектного updateEnvironment в пользовательском пути, устойчивый разбор отдельных сущностей.
- `web/index.html`, `dashboard.html`, `guide.html`, `login.html`, `service.js`: file-first onboarding, авторизация без репозиториев, практическая главная.
- `dist/app.js`, `articles.js`: короткая навигация, практические сценарии, происхождение метаданных, частичный разбор; убрать окружения/межпроектные графы из основного viewer.
- `lib/github.mjs` и соответствующие старые тесты/инструкции: удалить после удаления вызывающего кода.
- CLI импорта: каждый входной .e365 создаёт самостоятельный файл-проект; не добавлять обходной пользовательский путь импорта репозитория/каталога.
- README/AGENTS/privacy text: явно отразить новую политику сохранения оригиналов и отсутствие repository integration.

## 10. Минимальная приёмка

Не добавлять большой общий UI-suite на каждый текстовый патч. Для изменения этой функциональности нужны ограниченные проверки её границ:

- две загрузки с одинаковым code дают разные проекты; невалидный upload не создаёт пустой проект;
- второй владелец не получает ни один private endpoint;
- OAuth не запрашивает repo; старые repo endpoints недоступны;
- смешанный пакет сохраняет понятную часть и точный отчёт по неизвестной/повреждённой;
- опасный ZIP отклоняется, загруженный код никогда не исполняется;
- original/reparse/delete/restart и сохранение предыдущего индекса при ошибке;
- один сквозной desktop/mobile/keyboard сценарий: вход → файл → практическая задача → объект → назад.

При проверке текста отдельно проверить, что условная схема публикации не выглядит как реальная инфраструктура пользователя, а успех тестового widget round trip не выдаётся за доказанную готовность любой конфигурации к PROD.

## 11. Реализация и проверка

Новый пользовательский путь использует lib/project-parser.mjs и lib/projects.mjs. lib/store.mjs и lib/portals.mjs остаются только для чтения прежних индексов. Межпроектное объединение не используется для загрузок.

Проверки: npm test, npm run verify и npm run test:browser. Браузерный сценарий охватывает загрузку, задачу, поиск, исходный текст, отчёт, повторный разбор, удаление, мобильный экран и клавиатуру. Проверки выполняются только на синтетических данных.

Это реализация локального сервиса, а не production-выкладка. Для настоящего GitHub-входа нужен зарегистрированный OAuth App.
