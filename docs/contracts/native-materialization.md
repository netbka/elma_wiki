# Native materialization adapter (Wiki side)

Owner: #94 MR-03, PLAN-01 P6. Native counterpart: netbka/elma365#60. Product authority: [Solution-first](../SOLUTION_FIRST_PRODUCT_PLAN.md) and [working configuration release](../plans/working-configuration-release.md). Implementation: `lib/native-materialization.mjs`, `lib/native-materialization-e1.mjs` and the bridge transport `lib/native-materialization-bridge.mjs`. Inputs: [managed-workspace.md](managed-workspace.md) resolved revisions (P3), [native-coverage-adapter.md](native-coverage-adapter.md) units (P4) and [dependency-resolver.md](dependency-resolver.md) locks (P5).

This is the thin Wiki consumer of a native materialization service. It binds exact inputs, calls an injected native adapter and verifies the exact output. It assembles no package itself, stores nothing, adds no API/UI and never sets `publicationReady` or `executionEnabled`. P7 (#11 delivery coordinator) remains the only path to a candidate.

## Pinned native contract: `elma365-native-materialization@1` (E1)

netbka/elma365 PR #89 (merged 2026-10-14 as `23b476df735e60353a80b5aef6e827cca198a8be`) published E1 for #60: a request envelope, a validation receipt and manifest-regeneration policy `elma365-manifest-regeneration@1`, with a pure offline validator. netbka/elma365 PR #99 clarifies it as **schema revision 1.2** (still contract version 1): a no-edit mode, the output byte transport and wider data hygiene. #99 merged as `a6e5684d0e4bd3cb0cf82b6b4c0e8d663c80b7c1`. netbka/elma365 PR #104 adds **schema revision 1.3**: opt-in manifest-regeneration policy version 2 (`request.manifestPolicy`, receipt `manifestPolicy` version 1 or 2). Wiki pins revision 1.3 at its merge commit `3d819be5cfbb24c490d323ad845da050f01d6a5e` (`E1_SOURCE.merged: true`, schema sha256 `6cab239e81fb33bfadc3e667ab7f171feb4405cf10c6e8103141900b1729cb9c` over its LF bytes). Policy 1 traffic is unchanged: Wiki requests select no policy, and a receipt must name policy 1 (`manifest-policy-mismatch` otherwise). Wiki does not emit policy 2 yet, and a request selecting another policy is refused (`manifest-policy-unsupported`). Policy 2 request emission, with its profile-2 operation identity rule, is a follow-up. No native worker implements E1 yet. The existing `workspace.py stage` → `elma-dev compile` → `check.mjs` → `elma365pm pack` path is still a credentialed local CLI, and no process-runtime compiler or isolated assembler is published. `INSPECTED_NATIVE_MATERIALIZATION` records this revision, the contract and the facts still missing (`native-materialization-worker`, `baseline-preserving-stage-service`, `process-runtime-compiler`, `isolated-native-assembler`).

After schema review, `NATIVE_MATERIALIZATION_CONTRACTS` pins exactly E1 with its elma365 revision and schema digest; callers cannot extend it. `lib/contracts/elma365-native-materialization-1.schema.json` is a byte-for-byte copy of `tools/native-materialization/contract.schema.json` at that revision (sha256 and `schemaRevision` in `E1_SOURCE`; the digest is taken over LF bytes). `lib/native-materialization-e1.mjs` validates against it with the semantic and hygiene rules ported from elma365 `contract.mjs` at the same commit. Its JSON Schema subset rejects any keyword it does not implement, and a changed schema file (`E1_SCHEMA_INTACT` false) un-pins E1 and fails every validation as `contract-schema-drift`. An adapter under any other id or version returns `unavailable` with `native-materialization-contract-unavailable` and is never invoked. `SYNTHETIC_MATERIALIZATION_CONTRACT` exists only to test Wiki accounting. Its output always carries `synthetic-evidence-only` and is never `releaseEligible`.

No native worker is configured by default: `materializeNative` is called only with an injected adapter, and without one the result is `unavailable`. The [operator bridge transport](#operator-bridge-transport-materialize-job) below provides a production E1 adapter, but it exists only when explicitly configured. Pinning E1 and adding the transport therefore do not make native materialization work. They define what Wiki will accept from a future approved worker and how it travels.

### E1 adapter boundary

An adapter pinned to E1 (`id`, 40-hex `nativeRevision`, `contract: {id: 'elma365-native-materialization', version: 1}`) receives `{envelope, originals}` and returns `{receipt, artifacts: [{solution, bytes}]}`:

- **Request.** `buildE1Envelope` wraps the unmodified Wiki request as `{contract, request, originals[{artifactId, sha256, size}], releaseScope{solution, units, importOrder}}`, with scope taken from `request.inputs.coverage`. `validateE1Request` applies the E1 schema, the E1 semantic rules (inputs digest, base among originals, synthetic-basis accounting, dependency plan/profile/lock shape, compiler platform and coupled-service scope, operation shape and unit coverage, expected-file and manifest policy, original bytes/digest/size, release scope, no-edit mode) and E1 data hygiene (secret-like keys/values including HTTP Basic and URL user-info credentials, host paths and client host URLs whole or embedded in free text; ELMA API routes `/api/…`, `/pub/…` are exempt unless they contain `..`, a backslash or an encoded dot/separator). A request E1 rejects is `blocked` with `native-request-contract-invalid` and the error reasons, and the worker is never called.
- **No-edit mode.** A ready request with no changed component has `operations: []`. `prepareMaterializationRequest` then binds empty coverage `units` and `importOrder`, so the envelope's release scope is empty: nothing is imported (`no-edit-scope-not-empty` otherwise). Every expected file must be `preserve` from the base (`no-edit-file-not-preserved`), and a `validated` receipt reporting unexpected paths or replaced/removed/regenerated files is `no-edit-output-changed`.
- **Receipt.** `validateE1Receipt(receipt, request, { artifacts })` applies the receipt schema and binds it to `sha256(canonical(request))`, `inputsDigest`, the Target and compiler profile digests, and the E1 status rules. `validated` needs one artifact for the Solution, complete coverage equal to `request.expected`, and every required check (`original-digests`, `native-layout`, `expected-files`, `component-digests`, `manifest-regeneration`, `native-package-check`, `native-pack`, plus `service-compile` per changed coupled service) `passed` with tool, evidence reference and the artifact sha256. An `unavailable` receipt carries a reason and no artifact, coverage or check result, so relabelling it as validated makes it `invalid`. With `artifacts` (the returned `[{solution, bytes}]`, named by the digest of their bytes; `materializeNative` always passes them), the E1 output byte transport rule applies (`validateE1ReceiptArtifacts`, ported from elma365 `validateReceiptArtifacts`): every listed archive needs bytes of exactly its sha256 and size, and no other bytes may arrive (`missing-artifact-bytes`, `artifact-digest-mismatch`, `artifact-size-mismatch`, `duplicate-artifact`, `unexpected-artifact`, `artifact-name-invalid`). Bytes delivered with an `unavailable` receipt are therefore `unexpected-artifact`.
- **Outcome.** A receipt that is not a valid E1 receipt for this request (unknown field, unknown contract version, missing field, digest/profile mismatch, missing check, incomplete coverage, secret or host path, or a non-E1 response shape) fails as `native-receipt-invalid`. A worker revision other than the adapter's pinned `nativeRevision` fails as `native-worker-revision-mismatch`. A valid `unavailable` receipt returns `unavailable` with `native-worker-unavailable`. A valid `failed` receipt fails as `native-validation-failed`; when it lists an archive, that archive must also have been delivered with exactly its sha256 and size (or the receipt is `native-receipt-invalid`), and its bytes are never returned or used. Only a valid `validated` receipt, bound to the returned bytes, continues to Wiki's own output verification below. The manifest records the receipt status, worker and evidence reference.
- **Evidence basis.** `evidenceBasis` is `native` only when the adapter contract is native and the request itself has native evidence. A synthetic request materialized under E1 stays `synthetic` and keeps the `synthetic-evidence-only` blocker, so it is never `releaseEligible`.

### Review of E1 against this contract

E1 is compatible with Wiki's request and verification. Its `$defs/wikiRequest` is exactly the ready object `prepareMaterializationRequest` returns, and its digests are Wiki's canonical hashes. Revision 1.2 resolved the earlier open points on no-edit round trips, output byte transport and hygiene gaps (all above). Points that remain open:

1. **Stricter request formats.** E1 requires 64-hex Target/compiler/lock profile digests, a non-null import order and a compiler platform. `prepareMaterializationRequest` does not constrain these; E1 rejects them at the boundary instead.
2. **Manifest policy strictness.** E1 policy v1 also requires unchanged entity records to stay deep-equal and in order. Wiki checks non-entity manifest fields and component digests itself and relies on the worker's `manifest-regeneration` check for the stricter rule.
3. **Ancestry trust.** E1 trusts the base through its digest and supplied bytes; capture provenance is not part of v1.

Wiki's hygiene rules are defence in depth: Wiki builds requests from its own data, and raw credentials never enter it.

## Operator bridge transport (`materialize` job)

`lib/native-materialization-bridge.mjs` is the production E1 adapter `{envelope, originals} -> {receipt, artifacts}` over the existing [operator bridge](target-deployment.md#implemented-operator-bridge-adapter). It enqueues one `materialize` job on one owner's bridge, waits for the result with a timeout and returns the receipt plus the uploaded archive. It decides nothing: `materializeNative` validates the E1 request before the call and the receipt (`validateE1Receipt`, including sha256 and size binding) and the exact output bytes after it.

- **Configuration (opt-in).** `configuredMaterializationAdapter` reads non-secret variables: `WIKI_NATIVE_MATERIALIZATION_BRIDGE_ID` (bridge UUID), `WIKI_NATIVE_MATERIALIZATION_BRIDGE_OWNER` (owning user ID) and `WIKI_NATIVE_MATERIALIZATION_REVISION` (40-hex pinned worker revision), with optional `WIKI_NATIVE_MATERIALIZATION_TIMEOUT_MS` (default 30 min) and `WIKI_NATIVE_MATERIALIZATION_MAX_OUTPUT_BYTES` (default and cap 256 MiB). Any missing or malformed value leaves it `null`, so the `unavailable` behaviour is unchanged. The values are validated at startup: a non-integer, zero, negative or too large timeout (over 2^31-1 ms) or output limit (over 256 MiB), a bridge ID that is not a UUID or a revision that is not 40-hex disables the adapter and logs one reason naming the variable, never a configured value. With no variable set nothing is logged. `createServer` exposes the result as `server.nativeMaterialization`; no route or UI calls it yet.
- **Owner isolation.** Every call first reads the bridge as the configured owner; a bridge of another owner, or a removed bridge, fails before any job exists. The bridge token stays on the worker; jobs carry no credentials.
- **Configuration only.** `configuredMaterializationAdapter({env, bridges})` is the only way to obtain this adapter: it requires a store created by `bridgeStore()` and takes the worker revision from `WIKI_NATIVE_MATERIALIZATION_REVISION`, never from a caller. `materializeNative` treats any other adapter as non-native.
- **Fail-closed.** A timeout fences the job (`queued` becomes `cancelled`, `taken` becomes `unknown-outcome`) and the adapter throws `NATIVE_OUTCOME_UNKNOWN`, so the result is `failed` with `native-outcome-unknown`. A late worker result is recorded as `lateCompletion` evidence and never resumes the call. A failed job, a lost output file or a result that is not a receipt fails as well.
- **Shared queue; dedicated bridge recommended.** A `materialize` job uses the same per-bridge queue and worker as `health`, `inspect`, `deploy` and `readBack` jobs, and a worker takes one job at a time. A long native build therefore delays delivery jobs on that bridge, and vice versa. Configure a dedicated bridge (its own token and worker process) for materialization rather than reusing a delivery bridge.
- **Worker advertisement.** The worker may report `capabilities` on poll. Wiki records them on the bridge with `trusted: false` and uses them for nothing: eligibility comes only from the receipt and output checks above.

The wire shapes for the worker side (netbka/elma365#60) are in [the bridge contract](target-deployment.md#materialize-jobs-native-materialization).

### Zero-change requests and composed candidates

A zero-change (no-edit) request is valid E1 input and can be materialized for round-trip evidence, but it imports nothing: its coverage has no units and no import order. `lib/composed-candidates.mjs` freezes a composed candidate only with a native import order and at least one selected unit, so it refuses a zero-change build manifest with `A native import order is required` (409). This is intended: a candidate with nothing to import is not a delivery. The no-edit receipt remains build evidence only.

## Request: `prepareMaterializationRequest`

Input: workspace `state`, the incoming change `artifact`, its stored `resolution`, P4 `coverage` (an `adaptNativeCoverage` result over the resolved revision), P5 `dependencies` (a `resolveDependencyEvidence` result over `coverage.plan`), a `compiler` lock `{contract, profileDigest, platformVersion, evidenceRef, services}`, `targetProfile` `{digest, platformVersion}` and `originals`, a `Map` from artifact ID to private original bytes.

- The resolution must be `current` for the freshly recomputed B/A/C plan (`managedResolutionStatus`). A corrupt resolution blocks as `corrupt-resolution` and a moved plan as `stale-resolution`.
- Bytes come from the declared full base B and from each resolved component's chosen side: the incoming artifact, the accepted change named by `interventionId`, or the workspace baseline. Each source must be supplied and match its stored checksum. Otherwise the request blocks with `missing-original` or `original-checksum-mismatch`. The chosen component digest must exist in that artifact (`unlocatable-component-source`).
- Operations are whole-component `add | replace | remove`. All evidence files of a component (entity, side scripts, resources) come from one side, so coupled descriptor/source/runtime/resources cannot be mixed. A path shared by components with different chosen bytes blocks as `shared-path-conflict`.
- Expected files: every base path is `preserve` (exact sha256) unless a changed component owns it (`replace` with the chosen bytes, or `remove`). A file that the old version of a replaced component declared, but the new version does not, is `remove`. The service manifest of each changed service is `native-manifest`. Only its `entities` records may differ, and those are checked by component digests. `package.json` and unrelated manifests are preserved byte for byte. This is no blanket metadata exclusion.
- Evidence origin: `coverage` and `dependencies` must be results of `adaptNativeCoverage` and `resolveDependencyEvidence` in this process; anything else blocks as `unverified-native-coverage` / `unverified-dependency-resolution` and counts as absent. Requests and build manifests are likewise registered: `materializeNative` never claims native evidence for a request `prepareMaterializationRequest` did not return (`unverified-materialization-request`), and `lib/composed-candidates.mjs` records `releaseEligible` only from a manifest `materializeNative` returned (`isMaterializationManifest`). Only an adapter returned by `configuredMaterializationAdapter` (`isConfiguredMaterializationAdapter`) yields native evidence. It needs a store created by `bridgeStore()` and the worker revision from `WIKI_NATIVE_MATERIALIZATION_REVISION`; the factory taking a revision argument is not exported. Any other object with the E1 contract and a 40-hex revision still runs through the E1 checks, but its output is never `native` and, for native inputs, carries `unconfigured-native-adapter`.
- Trust marks are in-process. Every mark (bridge stores, configured adapters and observers, admitted observations, coverage and dependency results, requests, manifests) lives in a module-private `WeakSet`/`WeakMap` of the running process. A persisted, deserialized, copied or restarted object carries no mark, so it fails closed by design and must be re-derived from current inputs.
- P4: each changed component must be in exactly one selected native unit (`uncovered-resolved-component`, `duplicate-native-unit`). Every member of a selected unit must carry the resolved digest (`stale-native-unit-member`). Coverage blockers other than `synthetic-evidence-only` block as `native-coverage-incomplete`; plan blockers that the bound dependency resolution satisfied (its `remainingPlanBlockers`) no longer count. Under native coverage (`elma365-native-coverage@1`), `coverage.changesDigest` must equal the digest of this request's own changes (`stale-native-changes-binding`). Every changed component needs the pinned catalog's proven edit of exactly its operation (`unsupported-native-operation`). An operation proven on the synthetic fixture only (widget add/remove at catalog 1.1) keeps the request `synthetic`.
- P5: `dependencies.planDigest` must equal `planDigest(coverage.plan)` (`stale-dependency-resolution`), its blockers other than `synthetic-evidence-only` must be empty, and the Target profile must match both coverage and dependency evidence.
- Compiler: a missing lock blocks (`missing-compiler-profile`). Its platform must equal the Target's (`compiler-platform-mismatch`). Every changed coupled service (side scripts or `processor`) must be declared in `services` (`unsupported-compiler-scope`). The widget compiler does not certify process runtime.

`inputs` bind solution, resolution revision/result/plan digests, base and original checksums, coverage plan digest/units/import order, dependency plan digest/locks, compiler lock and Target profile. `inputsDigest` is their canonical hash. Any changed input produces a different digest. `evidenceBasis` is `native` only when both coverage and dependency evidence are native, `synthetic` when either is synthetic, and `unknown` otherwise.

## Materialization: `materializeNative`

A non-`ready` request returns `blocked` without calling the adapter. A pinned adapter (`id`, 40-hex `nativeRevision`, `contract`) receives the frozen request and copies of the required originals, and must return `{inputsDigest, artifacts: [{solution, bytes}], validation}`. An E1 adapter uses the envelope and receipt above instead, and a validated receipt is mapped to the same `validation`. Wiki then checks the output:

- An echoed `inputsDigest` mismatch fails as `stale-native-output`. Anything other than exactly one artifact for the Solution fails as `unexpected-native-artifacts`. A thrown adapter error becomes `native-materialization-failed` without leaking its message; an adapter error with code `NATIVE_OUTCOME_UNKNOWN` (timeout or lost worker result) becomes `native-outcome-unknown`. Both are `failed`, never `materialized`.
- Each expected path must be present with the exact bytes (`preserved-bytes-changed`, `replaced-bytes-mismatch`, `missing-output-path`) or absent (`removed-path-present`). Unplanned paths fail as `unexpected-output-path`. Native manifests must keep every non-entity field (`manifest-fields-changed`). The outer native layout, nested service ZIP or directory, must match the base (`native-layout-changed`).
- `parseManagedArtifact` over the output must yield exactly the expected component digests, with no new ambiguity.
- Native validation must be `passed` and name the exact output sha256, the adapter contract, the Target profile and the compiler profile. Otherwise it is `native-validation-missing` or `native-validation-mismatch`.

Determinism policy `unpacked-content-v1`: compare unpacked per-path bytes, component digests, outer layout and exact non-entity manifest fields. The ZIP container sha256 is recorded but not compared, because native packing timestamps may differ.

The result is a frozen build manifest bound to `requestDigest` and `inputsDigest`. It records adapter, artifact sha256/size, per-action file counts, validation and blockers, with a `manifestDigest`. Output bytes are returned only for a verified `materialized` result. `releaseEligible` requires a materialized output, native evidence and no blockers, so it is always false today. `materializeNative` also takes the P4 `coverage`: a materialized output with native evidence additionally needs `coverage.nativeEvidence.complete` for the same plan. Otherwise it carries `native-installation-evidence-incomplete` with the missing facts (`native-import-receipt`, `native-installation-observation`: P6/P8 native work), so even fully valid synthetic inputs under the pinned native contracts are never release-eligible. `materializationStatus(manifest, request)` returns `corrupt` for a tampered manifest, `stale` when the current request differs and `current` otherwise.

## Verification and current gap

`node --test test/native-materialization.test.mjs` uses synthetic Contracts-shaped B/A/C archives through the existing store. It covers an unknown contract id or version never being invoked; a no-edit round trip preserving every byte, resource, unknown manifest field and layout under a different container; a one-edit whole-component replacement, including removal of a resource the new version no longer declares; and two same-base changes with a resolved conflict and coupled client source. It also covers fail-closed output defects (dropped manifest field, changed preserved resource, extra/missing path, mixed coupled source, nested layout, missing/mismatched validation, stale echo, adapter failure) and fail-closed inputs (missing/altered original, missing/unsupported/mismatched compiler, missing/stale coverage, stale dependency plan/profile, corrupt and moved resolution, relocked compiler staling the manifest).

The E1 tests run a synthetic E1 worker around the test-only assembler. They cover a conforming envelope and validated receipt being accepted while synthetic inputs stay non-eligible. They cover malformed, mismatched-identity, unknown-version, relabelled, failed and unavailable receipts failing closed, a worker revision mismatch and a receipt for other bytes. They also cover requests E1 rejects (non-hex profile, missing/altered/unexpected original, size, release scope, host path, unknown field, contract version, inputs digest) being blocked before the worker. E1 1.2 tests cover the output transport binding (missing, other, duplicate, misnamed bytes, size, bytes with an unavailable receipt, and over the bridge an uploaded archive with a `failed` receipt that lists it ending as `native-validation-failed`), a zero-change request with an empty release scope accepted and materialized, the no-edit rejections, and elma365's hygiene positive/negative lists at the pinned commit. A parity run of elma365 `contract.mjs` at that commit against this module on the same edit and no-edit fixtures (request, receipt and output-byte mutations plus the hygiene lists) found no difference.

The native-contracts tests cover two cases. With current evidence (no observed Target profile, so no Target precondition and no verified receipt) a native widgets declaration still blocks. A fully valid synthetic declaration with verified synthetic receipts from an admitted bridge observation reaches `ready` with `evidenceBasis: native`, is accepted by E1 and materializes, but is never `releaseEligible`. They also cover a stale changes binding, a different Target profile and a synthetic-fixture-only add staying synthetic.

`node --test test/native-materialization-bridge.test.mjs` and the last test of `test/native-materialization.test.mjs` run a synthetic HTTP worker against a local Wiki server: success through the configured adapter (still `synthetic-evidence-only`), tampered and oversized uploads, size, digest and missing-bytes receipt binding, timeout and late result as unknown outcome, bearer/job/owner scoping of inputs and outputs, default-unconfigured behaviour and refusal of deploy semantics.

This is synthetic Wiki evidence only. Removal through validated tombstones is supported by the operation model but is not separately exercised here.

## Open P8 gate: native validation of exact output

The owner accepted this Wiki side of P6 on 2026-10-11 with the native-validation criterion deferred. Native materialization and native validation of exact physical Contracts output are an **open P8 gate** (PLAN-01 P8, #94 MR-07). The contract half is now pinned (E1, above). The gate still depends on an approved netbka/elma365#60 worker that executes E1 and returns a `validated` receipt for exact output bytes. It is **evidence-unavailable** here, not passed.

Until P8 observes a native `validated` E1 receipt for the exact output bytes from native (non-synthetic) inputs:

- no native worker is configured by default, so `materializeNative` returns `unavailable`; the bridge transport exists but no elma365 worker implements `materialize` yet; a worker answering with an E1 `unavailable` receipt also stays `unavailable`, and `releaseEligible` stays false;
- `SYNTHETIC_MATERIALIZATION_CONTRACT` is used only by `test/native-materialization.test.mjs`. Its output carries `synthetic-evidence-only`, has `evidenceBasis: synthetic` and is never native-valid or release-eligible;
- no build manifest from this adapter may feed a P7 candidate as native evidence. P7 ([target-deployment.md](target-deployment.md), composed candidates) freezes a manifest only after it re-derives this request from current Solution state. A synthetic or non-eligible candidate reaches only a synthetic training adapter.

Native materialization is not claimed to work.
