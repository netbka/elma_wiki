# Dependency and Target-profile evidence resolver

Owner: #94 MR-05 (PLAN-01 P5), Lane C in #91. Product authority: [Solution-first](../SOLUTION_FIRST_PRODUCT_PLAN.md) and [working configuration release](../plans/working-configuration-release.md). Implementation: `lib/dependency-resolver.mjs`. Upstream input: [release scope planner](release-scope-planner.md).

`resolveDependencyEvidence` is a synchronous pure accounting function over one `planReleaseScope` result. It returns a deeply frozen JSON-serializable record and performs no IO, provider call, licence purchase/provisioning, installation, decryption or deployment. It adds no store, API, UI or eligibility switch. `publicationReady` and `executionEnabled` always remain false. `resolutionComplete` means only that the supplied evidence has no accounting blockers under a native receipt contract; it is not native entitlement, activation or business acceptance.

## Inputs

- `plan`: planner output. Dependency prerequisites (`{from, service, namespace, code, status, candidates}`) are resolved; global-domain prerequisites stay with the planner. `planDigest` binds the result to the exact plan bytes.
- `targetProfile`: `{targetId, environment, digest, platformVersion, changedAt}`. All fields are required. Under a native receipt contract it is ignored and taken from `observation` (below). Every plan `targetPreconditions[].targetProfileDigest` must equal `digest`; no precondition (`unbound-plan-target-profile`) or a different/inconsistent one (`stale-target-profile`) blocks.
- `receiptContract`: `{id, version}` naming the receipt semantics. Only contracts in the module constant `NATIVE_RECEIPT_CONTRACTS` that declare provenance, expiry and compatibility semantics, or the test-only `SYNTHETIC_RECEIPT_CONTRACT`, are recognised. Callers cannot register one.
- `observation`: under a native receipt contract, the only source of the Target profile and of receipts: an admitted bridge Target profile observation (see below). Caller-supplied `receipts` there are not evaluated and block as `unobserved-native-receipt`.
- `receipts`: unique-ID rows `{id, contract, kind, status, provider: {code, version}, provides: [{service, namespace, code}], targetId, environment, targetProfileDigest, verifiedAt, expiresAt, provenance: {source: 'native-adapter', adapter, evidenceRef}, compatibility: {status, platformVersion, evidenceRef}, entitlement: {status, evidenceRef}, requiredBindings: [{name, kind}]}`. `kind: 'licensed-preinstallation'` also needs `activation: {status: 'verified', evidenceRef}`; `kind: 'official-distribution'` needs `distribution: {official: true, intact: true, artifactDigest, authorization: {status: 'authorized', evidenceRef}}`.
- `revocations`: `{receiptId, revokedAt}`; effective when `revokedAt <= now`.
- `bindings`: `{name, kind: 'secret-reference' | 'environment', reference, targetProfileDigest}`. Any other field, such as a value, is rejected; references never appear in the output.
- `distributionArtifacts`: privately held intact vendor artifacts `{code, version, sha256}`.
- `now`: explicit evaluation time; there is no implicit clock.

## Resolution

Without a recognised contract every dependency row is `unknown` with `native-receipt-contract-unavailable`; receipts are not evaluated. A prerequisite captured in several Solutions (`ambiguous-reference`) is `duplicate-provider`. The required provider is the single catalog candidate code and version; zero, several or versionless candidates block (`unknown-required-provider`, `ambiguous-provider`, `unknown-required-version`).

A receipt locks a prerequisite only when it names that exact reference and has none of these failures: contract mismatch; revoked; non-`verified` status or non-native provenance (`assertion-only-receipt`); provider/version mismatch; Target, environment or profile mismatch; unknown or future verification time; verification older than `targetProfile.changedAt` (`stale-receipt`); unknown or passed expiry; incompatible, unknown or platform-mismatched compatibility; unverified entitlement; unverified activation (preinstallation) or unofficial/altered, unauthorized, missing, ambiguous or digest-mismatched distribution artifact. Entitlement is required even when the catalog says `paid: false`. Catalog membership, readable paid bytes and a `paid` flag never satisfy any check. Verified receipts from different providers for one reference block as `duplicate-provider`; no winner is chosen. The selected receipt's required bindings must each match exactly one binding for the same profile, otherwise `missing-binding`, `ambiguous-binding`, `binding-profile-mismatch` or `unknown-required-bindings` blocks.

`locks` records provider, path, receipt, evidence reference, required binding names, profile digest and, for distribution, the artifact digest with `activation: 'pending-installation'`. `remainingPlanBlockers` is the plan's blockers minus the `missing-reference` / `unverified-licensed-prerequisite` rows whose prerequisite was locked; all other planner blockers stay. Output ordering is deterministic under input reordering, and inputs are not mutated.

## Synthetic evidence and the missing native contract

Positive results in this repository use `SYNTHETIC_RECEIPT_CONTRACT`. Such locks carry `evidence: 'synthetic'`, the result has `evidenceBasis: 'synthetic'` and a top-level `synthetic-evidence-only` blocker, so a synthetic resolution can never be complete.

## Pinned native contract: `elma365-dependency-receipt@1`

netbka/elma365 PR #103 (merged as `c202d6980e4bfaacf449a6b3b829b8c6580287a7`) publishes two sibling #60 contracts at **schema revision 1.1**. Wiki vendors them byte for byte with the generated capability catalog: `lib/contracts/elma365-native-coverage-1.schema.json` (sha256 `924ab59b40ebfc6fa5474148170415233193546bd79c888c212dac61a719f54d`), `lib/contracts/elma365-dependency-receipt-1.schema.json` (sha256 `788efb1e1b9eafb475c25b131d1d0ef0bbecd49c3360d117166cfd6adff89e19`) and `lib/contracts/elma365-native-coverage-1.capabilities.json` (sha256 `7bebdb365bbd9c61def8be7481efc6bf8419e6b84a15412c9458253f7f2136bb`, `catalogDigest` `52d87cd1d06b30635ff3fdc329a0ca1cdeb1e6c291dc88c8e4345bb585cf81ca`). Digests are over LF bytes. Revision 1.0 was an unmerged PR head and is never vendored. `lib/elma365-native-contracts.mjs` holds every pin in one place (`NATIVE_CONTRACT_SOURCE`, `COVERAGE_SOURCE`, `RECEIPT_SOURCE`, `CAPABILITY_CATALOG_SOURCE`). It validates with the E1 JSON Schema subset validator (`schemaValidator` in `lib/native-materialization-e1.mjs`) and the E1 hygiene scan, and ports the semantic rules of elma365 `tools/native-materialization/coverage.mjs` and `receipt.mjs` at that commit. A changed schema file makes `COVERAGE_SCHEMA_INTACT` or `RECEIPT_SCHEMA_INTACT` false and fails every validation as `contract-schema-drift`. A changed catalog leaves `CAPABILITY_CATALOG` null. Either way the contract is unpinned. Wiki cannot re-derive the catalog from the elma365 evidence table, so it pins the published digests instead (elma365 `validateCapabilityCatalog(..., {derive: false})`). To re-vendor a later revision, copy the three files from its merge commit and update the pins and any new semantic rules together.

`NATIVE_RECEIPT_CONTRACTS` pins exactly `{id: 'elma365-dependency-receipt', version: 1, semantics: {provenance: 'elma365-worker-read-only-observation-v1', expiry: 'verified-at-plus-at-most-P1D-and-stale-on-profile-change-v1', compatibility: 'observed-active-at-exact-version-on-exact-platform-v1'}}` with the revision and schema digest. The row is usable only while the vendored schema is intact and declares exactly these semantics.

Under it:

- The Target profile is `wikiTargetProfile(report)` of a schema- and semantically valid `observed` `$defs/targetProfileReport` (`{targetId, environment, digest: targetProfileDigest, platformVersion, changedAt}`); without one the result blocks with `unobserved-target-profile` and `unknown-target-profile`, and `evidenceBasis` is `unknown`.
- Receipts are only the report's own `receipts`. Each must also pass `validateDependencyReceipt(receipt, {report})`, otherwise `invalid-native-receipt`. That applies the schema, hygiene and the elma365 rules: `receipt-id-mismatch`, `duplicate-provided-reference`, `expiry-before-verification`, `expiry-exceeds-max-age` (more than one day), `kind-field-mismatch`, `unproven-verified-receipt` (a `verified` receipt without verified entitlement, compatible compatibility, observed bindings and verified activation, or official/intact/authorized distribution), and against the report `receipt-profile-mismatch`, `receipt-platform-mismatch` and `receipt-not-observed`. A self-inconsistent verified receipt is therefore never usable, and an `unverified` one stays `assertion-only-receipt`.
- `evidenceBasis` is `native-receipt` and locks carry `evidence: 'native-receipt'` only with an admitted observation. Official-distribution receipts cannot be observed (`receipt-not-observed`): authorization stays owner-reserved.

### Native Target profile observation (bridge seam)

Native receipts and the native Target profile reach Wiki only through the operator bridge's read-only `targetProfile` job (`lib/bridge.mjs`, `lib/native-materialization-bridge.mjs`). `configuredTargetProfileObserver({env, bridges})` returns `observe({targetId, environment, requirements})`, or `null` when unconfigured:

- It reads the same non-secret configuration as native materialization (`WIKI_NATIVE_MATERIALIZATION_BRIDGE_ID`, `_BRIDGE_OWNER`, `_REVISION`; optional `WIKI_NATIVE_TARGET_PROFILE_TIMEOUT_MS`). The expected worker revision is the configured `WIKI_NATIVE_MATERIALIZATION_REVISION`; no caller argument can choose it, and the factory that takes a revision is not exported.
- It accepts only a store created by `bridgeStore()` (`isBridgeStore`, a module-private registry). A stub with the same methods leaves observation unconfigured.
- It checks the owner's bridge, and enqueues nothing unless the worker advertises `targetProfile` in its capabilities (`unavailable`, `target-profile-observation-not-advertised`).
- The job payload is exactly `{contract, runId, targetId, environment, requirements}` with a fresh `runId`. The bridge store refuses an artifact, inputs or any other payload key (422), and fails a result that is anything but `{report}` (`target-profile-result-invalid`). A timeout or lost result throws `NATIVE_OUTCOME_UNKNOWN`.
- The report must pass `validateTargetProfileReport` (including 1.1 `unattested-observation`, `inventory-digest-mismatch`, `changed-after-observation`, `verified-without-evidence` and every receipt rule). Its `observation` provenance must be `{job: 'target-profile-observation', mode: 'read-only', transport: 'elma-dev-bridge', runId}` echoing the issued `runId`. It must also come from the pinned worker `nativeRevision`, for the requested Target and environment (`invalid` with the reasons otherwise). An `unavailable` report yields no observation.
- The resolver's result is registered as produced by `resolveDependencyEvidence` (`isDependencyResolution`); `prepareMaterializationRequest` refuses any other object as `unverified-dependency-resolution`, so a hand-built result claiming locks or completeness is never evidence.
- These marks are in-process only: a persisted, deserialized or restarted observation or result carries none and fails closed by design.
- An admitted observation is a frozen object registered inside the bridge module. `resolveDependencyEvidence` reads its report through `observedTargetProfileReport(observation)`, so a caller-built object of the same shape, a copy or a bare report is never evidence.

Nothing configures an observer by default, and no elma365 worker implements the `targetProfile` job yet (the elma365 offline producer reports `unavailable`; the live read-only job is named but not wired). The worker side must echo the Wiki-issued `runId` as `observation.runId`. Until a worker observes a Target, every actual dependency stays `unknown` and blocks release. Purchasing, licence provisioning, credential access and distribution rights remain owner-reserved ([`licences-accounts-providers`](../SOLUTION_FIRST_PRODUCT_PLAN.md#owner-reserved-matters-and-blockers)); the missing native Target observation (an elma365 worker implementing the read-only job) is B4 external evidence there.

This is synthetic repository evidence, not native, licence or live verification. No visible UI changed, so Storybook is not applicable.
