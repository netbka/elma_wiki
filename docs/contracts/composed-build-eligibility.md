# Composed build eligibility

Owner: #94 MR-04/MR-05, PLAN-01 C1. Product authority: [Solution-first](../SOLUTION_FIRST_PRODUCT_PLAN.md) and [working configuration release](../plans/working-configuration-release.md). Implementation: `lib/composed-build-eligibility.mjs`. Inputs: [release-scope-planner.md](release-scope-planner.md), [native-coverage-adapter.md](native-coverage-adapter.md), [dependency-resolver.md](dependency-resolver.md) and the bridge Target profile observation ([dependency-resolver.md](dependency-resolver.md#native-target-profile-observation-bridge-seam)). Screen: the composer in [target-deployment.md](target-deployment.md) (Solution composer screen).

`composedBuildEligibility({coverage, dependencies, observation, materialization, now})` decides whether the composer may offer a build. It is pure apart from reading the in-process provenance marks of its inputs, and returns a deeply frozen JSON-serializable record. It performs no IO, bridge job, provider call, materialization or Target selection, and enables nothing: `publicationReady` and `executionEnabled` are always false.

## Gates

A build is **eligible only when all five gates are `verified`**. Each gate is `verified` (no reasons), `blocked` (evidence present but failing) or `unknown` (evidence absent or not produced by its owner). Every reason row is kept verbatim from its source with its details (component, unit, module, fact).

| Gate | Evidence accepted | Typical blocking reasons |
| --- | --- | --- |
| `scope` | The planner output inside an `adaptNativeCoverage` result (`isNativeCoverageResult`). Planner blockers that a bound dependency resolution locked are dropped (its `remainingPlanBlockers`). | `dependency-cycle`, `missing-component`, `incomplete-capture`, `incomplete-solution-inventory`, global-domain gaps |
| `coverage` | The same adapter result with `evidenceBasis: 'native'` and complete native evidence. Native unit planner reasons belong here. | `native-coverage-unavailable`, `unknown-native-import-unit`, `unsupported-native-unit-member` (an unknown object kind), `synthetic-evidence-only`, `missing-native-evidence` per fact (`native-import-receipt`, `native-installation-observation`, global handlers) |
| `dependencies` | A `resolveDependencyEvidence` result (`isDependencyResolution`) whose `planDigest` equals the coverage plan, with `evidenceBasis: 'native-receipt'`. Dependency prerequisite reasons of the planner belong here. | `missing-reference`, `unverified-licensed-prerequisite`, `unresolved-dependency` with the resolver's details (`missing-receipt`, `assertion-only-receipt`, `unverified-entitlement`, `missing-binding`, ...), `stale-dependency-resolution`, `native-receipt-contract-unavailable`, `synthetic-evidence-only` |
| `target-profile` | An admitted bridge observation (`observedTargetProfileReport`) whose report is valid (`wikiTargetProfile`), observed within `TARGET_PROFILE_MAX_AGE_MS` (one day, the receipt expiry of `elma365-dependency-receipt@1`) and equal to the profile every input was planned for. Target reasons of the planner, adapter and resolver belong here. | `unobserved-target-profile`, `stale-target-profile-observation`, `stale-coverage-profile`, `stale-dependency-profile`, `stale-native-profile`, `unknown-target-precondition`, `unproven-target-preservation` |
| `materialization` | `{available: true}` reported by the server ([composer build capability](native-materialization.md#composer-build-route-plan-01-c2)). An unreported capability is `unknown`. | `native-materialization-unavailable` with its `detail` (for example `native-materialization-unconfigured`, `materialization-bridge-offline`) and the missing native pieces |

A copy, deserialized object or hand-built record claiming coverage, locks or an observed profile is never evidence (`unverified-native-coverage`, `unverified-dependency-resolution`, `unobserved-target-profile`). A paid flag, catalog membership or readable paid bytes never satisfy a dependency; only a verified receipt observed on the same Target profile does.

Because the coverage adapter always reports native installation evidence as incomplete (P6/P8) and no native builder runs (netbka/elma365#60), **no composed build is eligible today**. The gates name what remains instead of presenting the build as working.

## Service wiring

`solutionBuildEvidence({capture, declarations, observation, changes, compiler, receiptContract, now})` runs the real pipeline for one Solution's build inputs: `adaptNativeCoverage` (request `solution`) over the capture, its changes and the given native declarations, then `resolveDependencyEvidence` under the pinned native receipt contract. It returns `{coverage, dependencies, observation, compiler}`. `solutionBuildEligibility({capture, declarations, observation, changes, materialization, receiptContract, now})` evaluates the gates over the same evidence. The eligibility route and the build route both use `solutionBuildEvidence`, so the composer shows exactly the evidence a build would use.

**Build inputs** are server-derived only (`buildInputs` in `server.mjs`, `composedBuildInputs` in `lib/native-build-evidence.mjs`). With an accepted merge they are the resolved revision: `prepareMaterializationRequest` over the stored pre-acceptance state, resolution and original bytes yields the E1 change rows (`changesFromRequest`, plus each component's kind), and `resolvedBuildCapture` builds the capture: every resulting component at its resolved digest, checksum = the resolution's `resultDigest`, ambiguities and unclassified files from the baseline and every contributing artifact, and every dependency declaration of those artifacts except one whose source component was removed. A contributing artifact without a dependency inventory leaves it unknown (`unknown-dependency-inventory`). So a merge never drops a paid, missing or unknown declaration. Without an accepted merge the inputs are the accepted full capture with no changes. Inputs whose request is itself blocked (`missing-original`, `stale-resolution`, an accepted merge that cannot be used, ...) carry `blockers`; no build evidence is requested for them.

`GET /api/solutions/:id/composed-eligibility` (authenticated, read-only; 404 without a session or for an unknown Solution, 405 for other methods, 409 without an accepted full capture) returns `{solutionId, revision, ...eligibility}` over the Solution's build inputs (above). The route itself never observes and never requests evidence: it uses only the observation and native build evidence the operator refresh below already admitted for exactly the current Solution binding, and adds `targetProfileRefresh` (the refresh state, see below). Without them the route reports `scope` verified for a clean capture and every other gate blocked or unknown with its reasons; an observation alone removes `unobserved-target-profile`, but without a native coverage declaration the plan stays unbound to the profile (`unbound-plan-target-profile`). With admitted, current build evidence the declaration binds the plan to the profile; what remains blocked is what native evidence does not establish: unverified paid dependencies (`dependencies`), unsupported or unknown kinds (`coverage`), an existing Target without a proven preservation policy (`unproven-target-preservation`), and the post-build facts `native-import-receipt` and `native-installation-observation`. Materialization uses the same capability as `GET /api/delivery/capabilities` `composedBuild`. The build route `POST /api/solutions/:id/composed-build` evaluates these gates over its own evidence and starts a build only when every gate is verified apart from the post-build installation facts ([composer build route](native-materialization.md#composer-build-route-plan-01-c2)).

## Operator Target profile refresh

`lib/target-profile-refresh.mjs` (`targetProfileRefresh({env, bridges})`) is the only service path that runs the bridge's read-only `targetProfile` job ([bridge seam](dependency-resolver.md#native-target-profile-observation-bridge-seam)). It wraps `configuredTargetProfileObserver` over the server's own bridge store and the same `WIKI_NATIVE_MATERIALIZATION_*` / `WIKI_NATIVE_TARGET_PROFILE_*` configuration. It is offered only when that observer is configured **and** its Target is designated for observation (`OBSERVATION_TARGETS`: `dev2` only); otherwise the state is `target-profile-observation-unconfigured` or `target-not-designated`.

`POST /api/solutions/:id/target-profile` (authenticated; 404 without a session or for an unknown Solution, 405 for other methods, 415 without JSON) takes exactly `{expectedRevision}`. Any other key, such as a Target, environment, bridge, owner, report, receipts or requirements, is `400 invalid-request`: bridge, owner, Target, worker revision and receipt requirements are server-derived (requirements are the capture plan's prerequisites with exactly one catalog provider, `observationRequirements`). Refusals: `409 unavailable` when not configured or not designated; `403 operator-only` unless the session user is the configured bridge owner (`WIKI_NATIVE_MATERIALIZATION_BRIDGE_OWNER`), because shared content access is not bridge control; `409 in-progress` while another refresh of the Solution runs; `409 no-accepted-capture`; `409 stale-solution-revision`. One accepted request enqueues exactly one `targetProfile` job with a fresh run id and, only after it is admitted, at most one `buildEvidence` job with its own fresh run id ([native build evidence](#native-build-evidence)). Outcomes: `201 observed` (admitted), `409 unavailable` (the worker's reason, or `target-profile-bridge-failed`), `422 invalid` (the observer's errors: schema, `unattested-observation` for a foreign or replayed run id, `native-worker-revision-mismatch`, `target-mismatch`, ...), `502 unknown` (timeout or lost result) and `409 stale-solution-binding` when the Solution moved while the worker observed. Every completed attempt returns the refreshed `targetProfileRefresh`.

An admitted observation is kept in process memory only, per Solution, with the binding it was requested for: `managed.buildCapture(...).binding` = Solution id, revision, status, capture id and checksum, review-events digest and the accepted merge (artifact, revision, resolution id, result digest). It is used only while that binding is unchanged, the observer is still configured and the observation still carries its provenance mark; its age is judged by the `target-profile` gate (one day). Any other outcome of a later refresh drops it. A restart, a copy or a deserialized observation is never evidence. Nothing observes automatically: no read, page load, build or retry enqueues a job, and a lost or unknown result is not replayed.

`targetProfileRefresh` in the eligibility response is `{configured, reason, target, operator, inProgress, current, staleInputs, last: {outcome, at, reason, errors, targetProfile} | null}`. `current` means the admitted observation is used for this binding; `staleInputs` means one is held for a previous binding and ignored.

### Native build evidence

After an admitted observation the same refresh requests native build evidence, `elma365-native-build-evidence@1` (netbka/elma365 PR #112, merged as `00a29fb`; contract `docs/enterprise-development/native-build-evidence.md` there), through the bridge's read-only `buildEvidence` job (`lib/native-build-evidence.mjs`, `configuredBuildEvidenceSource`). Configuration is the same as the observer's (`WIKI_NATIVE_MATERIALIZATION_BRIDGE_ID`, `_BRIDGE_OWNER`, `_REVISION`, `WIKI_NATIVE_TARGET_PROFILE_TARGET`; optional `WIKI_NATIVE_BUILD_EVIDENCE_TIMEOUT_MS`, default 5 minutes). Nothing else requests it: no read, page load, build or retry.

- **Payload.** Exactly `{contract, runId, targetId, environment, nativeRevision, captures, changes}`: a fresh run id per job, the configured Target as both `targetId` and `environment`, the configured worker revision and the server-derived build inputs projected to `{solution, checksum, components: [{key, service, kind, digest}]}` and `{solution, key, op, digest, service, kind}`. The caller supplies none of it. A request the contract cannot carry (`validateBuildEvidenceRequest`) is not sent (`build-evidence-request-unsupported`). A worker that does not advertise `buildEvidence` is never sent one (`build-evidence-not-advertised`); the advertisement only disables.
- **Admission.** `validateBuildEvidence` is the elma365 consumer rule set ported rule for rule: exact keys and hygiene, contract, `requestDigest = sha256(canonical(payload))`, producer `{build-evidence, read-only, elma-dev-bridge}` with the issued run id, Target, the pinned worker revision, freshness (15 minutes, 2 minutes skew), every `NOT_ESTABLISHED` fact listed in `missing`, a widget-only compiler lock bound to the document's profile and evidence reference, and a coverage declaration that re-derives against the vendored capability catalog (`catalogDigest 60048542…b58c`) for exactly the payload's captures and changes. Unit preconditions must name the observation Wiki admitted, and `profile.targetProfileDigest` must equal its report's digest (`stale-target-profile`). Only a valid `produced` document is admitted: it is frozen, registered in process memory (`admittedBuildEvidence`) and held with the observation under the same binding. A copy or deserialized document is never evidence.
- **Use.** `currentBuildEvidence` re-checks at every eligibility read and build: the document must still be admitted, held with the same admitted observation, for the same configured revision, for byte-identical captures and changes re-derived now (`stale-build-evidence-inputs`) and still valid now (`stale-evidence` after 15 minutes). Then its coverage declaration goes to `adaptNativeCoverage` and its compiler lock to `prepareMaterializationRequest` verbatim; the Target profile remains the admitted observation's.
- **Outcomes** (`targetProfileRefresh.buildEvidence.last.outcome`): `produced`, `unavailable` (the worker's `worker-profile-unbound` or `capability-catalog-unavailable`, `build-evidence-not-advertised`, `build-evidence-bridge-failed`), `invalid` (the validation reasons, for example `foreign-run`, `request-mismatch`, `target-mismatch`, `worker-revision-mismatch`, `stale-evidence`, `unsupported-compiler-scope`, `hidden-missing-fact`, `over-claim`, `invalid-coverage-declaration`), `unknown` (timeout or lost result) and `not-requested` (`unbuildable-inputs`). None of them affects the admitted profile; none is replayed.

`targetProfileRefresh.buildEvidence` in the eligibility response is `{configured, current, expired, last: {outcome, at, reason, errors, missing, issuedAt, compilerServices} | null, use: {status, reason}, inputBlockers}`. `use` is the server's verdict for the current inputs (`current`, or `missing`/`stale` with its reason).

Native build evidence never establishes licences, activation, compatibility, required bindings, a process runtime compiler, a native import or a Target installation (elma365 `NOT_ESTABLISHED`). Paid prerequisites therefore stay `unverified-licensed-prerequisite` until a verified receipt is observed; a changed process template stays `unsupported-native-unit-member` / `unsupported-native-operation` and its service is outside the widget-only compiler lock (`unsupported-compiler-scope`); and the post-build facts stay separate test-install/release gates (`native-installation-evidence-incomplete`). No build evidence is native, installation, licence or business acceptance.

The build route's trusted evidence (`createServer` `buildEvidence`) defaults to this source: the observation and, when current, the build evidence admitted for the Solution's current binding, through `solutionBuildEvidence` over the inputs re-derived from the build's own loaded state. The build answers `blocked` with the named gates until every gate apart from the post-build facts is verified.

## Composer

The composer (`web/managed/composer.js`) reads the route next to the capability. «Собрать конфигурацию» stays disabled unless the builder is available **and** every gate is verified. The «Условия сборки» list shows each gate with its status and every blocking reason with a Russian label (`buildBlockReasons` in `web/managed/labels.js`); an unknown reason key stays visible with a neutral label, and more than five rows of one reason are counted. A failed eligibility read shows its own notice and keeps the build disabled. `solutionNextAction` offers `build` only under the same condition; otherwise `build-blocked`.

The «Профиль Target» group (`targetProfileView`, `targetProfileFailureView`, `buildEvidenceView`) also shows «Сведения о сборке»: not yet received, current for this version (with the compiler scope and every fact it does not confirm), older than 15 minutes, for a previous version, unavailable, rejected, unknown and not requested, each with its reasons. Only the server's `use` verdict makes it current. The group shows the refresh state in the same renderer: not configured, Target not designated, not yet read, reading, read for the current version (Target, platform, digest prefix, time), read for a previous version (stale inputs), unavailable, rejected report, unknown result and moved Solution, each with its reasons. «Прочитать профиль Target DEV2» is offered only to the operator with a known Solution revision; other participants see that only the bridge operator may read it. One click sends one request; a moved Solution, a running read, an unknown result or a lost response disable it until a fresh read («Обновить состояние»), and a rejected report may be retried by hand. On success the page re-reads the composer.

## Verification

`node --test test/composed-build-eligibility.test.mjs test/solution-composer-view.test.mjs` covers: absent and hand-built evidence; a diamond dependency graph planning a verified scope while synthetic coverage and receipts keep the build ineligible; a component cycle; the native path (native declaration, admitted bridge observation, native receipts) where only native installation evidence and the builder remain; a missing paid dependency, an unverified entitlement receipt and a verified licensed preinstallation; an unknown object kind; stale profiles (an observation older than a day, coverage or dependencies planned for another profile, a declaration for another profile, a resolution of another plan); order independence and immutability; today's service over a parsed capture; and the HTTP route. The composer view tests cover each gate's labels and reasons, capping, failed or malformed eligibility, the next action and every Target profile refresh state and failure. Storybook: `solution-composer--build-gates`, `solution-composer--eligibility-load-error` and `solution-composer--profile-*` (unconfigured, not operator, ready, progress, observed, stale, unavailable, invalid, unknown, moved, lost, evidence, evidence-unavailable, evidence-invalid); check: `npm run test:composer:storybook`. The production page check `npm run test:composer:browser` posts exactly `{expectedRevision}` once, re-reads after success and never replays a stale or lost refresh.

`node --test test/target-profile-refresh.test.mjs` covers the refresh route over a real bridge store and an in-process synthetic HTTP worker: unconfigured and non-designated bridges, another operational actor, malformed and caller-supplied Target/bridge/report fields, a stale revision, GET without side effects, one observed `dev2` job with the server-derived payload feeding eligibility, a changed Solution making it stale, a restart dropping it, unavailable, replayed, foreign, lost and moved results never enabling the gate, and one refresh at a time. `node --test test/native-build-evidence.test.mjs` covers contract parity with the elma365 vectors (produced documents accepted; replayed, foreign, stale, future, retargeted and other-revision documents, changed captures and changes, relabelled unsupported kinds, `processor`/empty/duplicate compiler scopes, over-claims, hidden facts, unavailable documents carrying evidence, extra keys, host paths, unobserved preconditions, another observation or profile and a missing catalog rejected with the elma365 reasons), strict requests, admission over a real bridge store (copies, other inputs, observation, revision and expiry never current; unavailable, foreign and lost answers never admitted; an unadvertised worker never sent a job; the store refusing extra payload keys and artifacts), configuration, server-derived inputs (resolved capture and change rows, a moved state invalidating the resolution, missing originals) and paid/missing/unknown dependency declarations surviving the merge. `test/composed-build.test.mjs` drives the production default through HTTP: one operator refresh enqueues one `targetProfile` and one `buildEvidence` job with the server-derived payload; the displayed gates and the build then agree, the build validates and freezes while `releaseEligible` stays false; a later accepted change makes the held evidence stale; and unavailable, foreign, other-request, retargeted, other-worker, stale, other-profile, processor-compiler, over-claiming, fact-hiding and malformed answers never become evidence or start a build. All evidence is synthetic; no native build or live Target is involved, and no live dev2 observation, build evidence or native acceptance is claimed.
