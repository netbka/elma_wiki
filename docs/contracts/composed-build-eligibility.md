# Composed build eligibility

Owner: #94 MR-04/MR-05, PLAN-01 C1. Product authority: [Solution-first](../SOLUTION_FIRST_PRODUCT_PLAN.md) and [working configuration release](../plans/working-configuration-release.md). Implementation: `lib/composed-build-eligibility.mjs`. Inputs: [release-scope-planner.md](release-scope-planner.md), [native-coverage-adapter.md](native-coverage-adapter.md), [dependency-resolver.md](dependency-resolver.md) and the bridge Target profile observation ([dependency-resolver.md](dependency-resolver.md#native-target-profile-observation-bridge-seam)). Screen: the composer in [target-deployment.md](target-deployment.md) (Solution composer screen).

`composedBuildEligibility({coverage, dependencies, observation, materialization, now})` decides whether the composer may offer a build. It is pure apart from reading the in-process provenance marks of its inputs, and returns a deeply frozen JSON-serializable record. It performs no IO, bridge job, provider call, materialization or Target selection, and enables nothing: `publicationReady` and `executionEnabled` are always false.

## Gates

A build is **eligible only when all five gates are `verified`**. Each gate is `verified` (no reasons), `blocked` (evidence present but failing) or `unknown` (evidence absent or not produced by its owner). Every reason row is kept verbatim from its source with its details (component, unit, module, fact).

| Gate | Evidence accepted | Typical blocking reasons |
| --- | --- | --- |
| `scope` | The planner output inside an `adaptNativeCoverage` result (`isNativeCoverageResult`). Planner blockers that a bound dependency resolution locked are dropped (its `remainingPlanBlockers`). | `dependency-cycle`, `missing-component`, `incomplete-capture`, `incomplete-solution-inventory`, global-domain gaps |
| `coverage` | The same adapter result with `evidenceBasis: 'native'` and complete native evidence. Native unit planner reasons belong here. | `native-coverage-unavailable`, `unknown-native-import-unit`, `unsupported-native-unit-member` (an unknown object kind), `synthetic-evidence-only`, `missing-native-evidence` per fact (`native-import-receipt`, `native-installation-observation`, global handlers) |
| `dependencies` | A `resolveDependencyEvidence` result (`isDependencyResolution`) whose `planDigest` equals the coverage plan, with `evidenceBasis: 'native-receipt'`. Dependency prerequisite reasons of the planner belong here. | `missing-reference`, `unverified-licensed-prerequisite`, `unresolved-dependency` with the resolver's details (`missing-receipt`, `assertion-only-receipt`, `unverified-entitlement`, `missing-binding`, ...), `stale-dependency-resolution`, `native-receipt-contract-unavailable`, `synthetic-evidence-only` |
| `target-profile` | An admitted bridge observation (`observedTargetProfileReport`) whose report is valid (`wikiTargetProfile`), observed within `TARGET_PROFILE_MAX_AGE_MS` (one day, the receipt expiry of `elma365-dependency-receipt@1`) and equal to the profile every input was planned for. Target reasons of the planner, adapter and resolver belong here. | `unobserved-target-profile`, `stale-target-profile-observation`, `stale-coverage-profile`, `stale-dependency-profile`, `stale-native-profile`, `unknown-target-precondition`, `unproven-target-preservation` |
| `materialization` | `{available: true}` reported by the server ([composer build capability](native-materialization.md#composer-build-route-plan-01-c2)). An unreported capability is `unknown`. | `native-materialization-unavailable` with its `detail` (for example `native-materialization-unconfigured`, `materialization-bridge-offline`) and the missing native pieces |

A copy, deserialized object or hand-built record claiming coverage, locks or an observed profile is never evidence (`unverified-native-coverage`, `unverified-dependency-resolution`, `unobserved-target-profile`). A paid flag, catalog membership or readable paid bytes never satisfy a dependency; only a verified receipt observed on the same Target profile does.

Because the coverage adapter always reports native installation evidence as incomplete (P6/P8) and no native builder runs (netbka/elma365#60), **no composed build is eligible today**. The gates name what remains instead of presenting the build as working.

## Service wiring

`solutionBuildEligibility({capture, declarations, observation, changes, materialization, receiptContract, now})` runs the real pipeline for one Solution: `adaptNativeCoverage` (request `solution`) over the accepted full capture, `resolveDependencyEvidence` under the pinned native receipt contract, then the gates.

`GET /api/solutions/:id/composed-eligibility` (authenticated, read-only; 404 without a session or for an unknown Solution, 405 for other methods, 409 without an accepted full capture) returns `{solutionId, revision, ...eligibility}`. The capture is the Solution's accepted full baseline (`managed.buildCapture`). The service holds no native coverage declaration source and requests no Target profile observation: only the P8 operator path may run the bridge's read-only `targetProfile` job. So today the route reports `scope` verified for a clean capture and every other gate blocked or unknown with its reasons. Materialization uses the same capability as `GET /api/delivery/capabilities` `composedBuild`. The build route `POST /api/solutions/:id/composed-build` evaluates these gates over its own evidence and starts a build only when every gate is verified apart from the post-build installation facts ([composer build route](native-materialization.md#composer-build-route-plan-01-c2)).

The composer (`web/managed/composer.js`) reads the route next to the capability. «Собрать конфигурацию» stays disabled unless the builder is available **and** every gate is verified. The «Условия сборки» list shows each gate with its status and every blocking reason with a Russian label (`buildBlockReasons` in `web/managed/labels.js`); an unknown reason key stays visible with a neutral label, and more than five rows of one reason are counted. A failed eligibility read shows its own notice and keeps the build disabled. `solutionNextAction` offers `build` only under the same condition; otherwise `build-blocked`.

## Verification

`node --test test/composed-build-eligibility.test.mjs test/solution-composer-view.test.mjs` covers: absent and hand-built evidence; a diamond dependency graph planning a verified scope while synthetic coverage and receipts keep the build ineligible; a component cycle; the native path (native declaration, admitted bridge observation, native receipts) where only native installation evidence and the builder remain; a missing paid dependency, an unverified entitlement receipt and a verified licensed preinstallation; an unknown object kind; stale profiles (an observation older than a day, coverage or dependencies planned for another profile, a declaration for another profile, a resolution of another plan); order independence and immutability; today's service over a parsed capture; and the HTTP route. The composer view tests cover each gate's labels and reasons, capping, failed or malformed eligibility and the next action. Storybook: `solution-composer--build-gates` and `solution-composer--eligibility-load-error`; check: `npm run test:composer:storybook`. All evidence is synthetic; no bridge job, native build or live Target is involved.
