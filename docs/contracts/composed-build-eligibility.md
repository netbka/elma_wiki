# Composed build eligibility

Owner: #94 MR-04/MR-05, PLAN-01 C1. Product authority: [Solution-first](../SOLUTION_FIRST_PRODUCT_PLAN.md) and [working configuration release](../plans/working-configuration-release.md). Implementation: `lib/composed-build-eligibility.mjs`. Inputs: [release-scope-planner.md](release-scope-planner.md), [native-coverage-adapter.md](native-coverage-adapter.md), [dependency-resolver.md](dependency-resolver.md) and the bridge Target profile observation ([dependency-resolver.md](dependency-resolver.md#native-target-profile-observation-bridge-seam)). Screen: the composer in [target-deployment.md](target-deployment.md) (Solution composer screen).

`composedBuildEligibility({coverage, dependencies, observation, materialization, now})` decides whether the composer may offer a build. It is pure apart from reading the in-process provenance marks of its inputs, and returns a deeply frozen JSON-serializable record. It performs no IO, bridge job, provider call, materialization or Target selection, and enables nothing: `publicationReady` and `executionEnabled` are always false.

## Gates

A build is **eligible only when all five gates are `verified`**. Each gate is `verified` (no reasons), `blocked` (evidence present but failing) or `unknown` (evidence absent or not produced by its owner). Every reason row is kept verbatim from its source with its details (component, unit, module, fact).

| Gate | Evidence accepted | Typical blocking reasons |
| --- | --- | --- |
| `scope` | The planner output inside an `adaptNativeCoverage` result (`isNativeCoverageResult`). Planner blockers that a bound dependency resolution locked are dropped (its `remainingPlanBlockers`). | `dependency-cycle`, `missing-component`, `incomplete-capture`, `incomplete-solution-inventory`, global-domain gaps |
| `coverage` | The same adapter result with `evidenceBasis: 'native'` and complete native evidence. Native unit planner reasons belong here. | `native-coverage-unavailable`, `unknown-native-import-unit`, `unsupported-native-unit-member` (an unknown object kind), `synthetic-evidence-only`, `missing-native-evidence` per fact (`native-import-receipt`, `native-installation-observation`, global handlers) |
| `dependencies` | A `resolveDependencyEvidence` result (`isDependencyResolution`) whose `planDigest` equals the coverage plan, with `evidenceBasis: 'native-receipt'`. Dependency prerequisite reasons of the planner belong here. | `missing-reference`, `unverified-licensed-prerequisite`, `unresolved-dependency` with the resolver's details (`missing-receipt`, `assertion-only-receipt`, `unverified-entitlement`, `missing-binding`, ...), `stale-dependency-resolution`, `native-receipt-contract-unavailable`, `synthetic-evidence-only` |
| `target-profile` | An admitted bridge observation (`observedTargetProfileReport`) whose report is valid (`wikiTargetProfile`), observed within `TARGET_PROFILE_MAX_AGE_MS` (one day, the receipt expiry of `elma365-dependency-receipt@1`) and equal to the profile every input was planned for. Target reasons of the planner, adapter and resolver belong here. | `unobserved-target-profile`, `stale-target-profile-observation`, `stale-coverage-profile`, `stale-dependency-profile`, `stale-native-profile`, `unknown-target-precondition`, `unproven-target-preservation` |
| `materialization` | `{available: true}` reported by the server ([composer build capability](native-materialization.md#composer-build-route-plan-01-c2)). An unreported capability is `unknown`. | `native-materialization-unavailable` with its `detail` (for example `native-materialization-unconfigured`, `materialization-bridge-offline`) and the missing native pieces |

A copy, deserialized object or hand-built record claiming coverage, locks or an observed profile is never evidence (`unverified-native-coverage`, `unverified-dependency-resolution`, `unobserved-target-profile`). A paid flag, catalog membership or readable paid bytes never satisfy a dependency; only a verified receipt observed on the same Target profile does.

Because the coverage adapter always reports native installation evidence as incomplete (P6/P8) and no native builder runs (netbka/elma365#60), **no composed build is eligible today**. The gates name what remains instead of presenting the build as working.

## Service wiring

`solutionBuildEligibility({capture, declarations, observation, changes, materialization, receiptContract, now})` runs the real pipeline for one Solution: `adaptNativeCoverage` (request `solution`) over the accepted full capture, `resolveDependencyEvidence` under the pinned native receipt contract, then the gates.

`GET /api/solutions/:id/composed-eligibility` (authenticated, read-only; 404 without a session or for an unknown Solution, 405 for other methods, 409 without an accepted full capture) returns `{solutionId, revision, ...eligibility}`. The capture is the Solution's accepted full baseline (`managed.buildCapture`). The service holds no native coverage declaration source. The route itself never observes: it uses only an observation the operator refresh below already admitted for exactly the current Solution binding, and adds `targetProfileRefresh` (the refresh state, see below). So today the route reports `scope` verified for a clean capture and every other gate blocked or unknown with its reasons; after an admitted observation `unobserved-target-profile` is gone, but without a native coverage declaration the plan stays unbound to the profile (`unbound-plan-target-profile`), coverage stays blocked and nothing becomes eligible. Materialization uses the same capability as `GET /api/delivery/capabilities` `composedBuild`. The build route `POST /api/solutions/:id/composed-build` evaluates these gates over its own evidence and starts a build only when every gate is verified apart from the post-build installation facts ([composer build route](native-materialization.md#composer-build-route-plan-01-c2)).

## Operator Target profile refresh

`lib/target-profile-refresh.mjs` (`targetProfileRefresh({env, bridges})`) is the only service path that runs the bridge's read-only `targetProfile` job ([bridge seam](dependency-resolver.md#native-target-profile-observation-bridge-seam)). It wraps `configuredTargetProfileObserver` over the server's own bridge store and the same `WIKI_NATIVE_MATERIALIZATION_*` / `WIKI_NATIVE_TARGET_PROFILE_*` configuration. It is offered only when that observer is configured **and** its Target is designated for observation (`OBSERVATION_TARGETS`: `dev2` only); otherwise the state is `target-profile-observation-unconfigured` or `target-not-designated`.

`POST /api/solutions/:id/target-profile` (authenticated; 404 without a session or for an unknown Solution, 405 for other methods, 415 without JSON) takes exactly `{expectedRevision}`. Any other key, such as a Target, environment, bridge, owner, report, receipts or requirements, is `400 invalid-request`: bridge, owner, Target, worker revision and receipt requirements are server-derived (requirements are the capture plan's prerequisites with exactly one catalog provider, `observationRequirements`). Refusals: `409 unavailable` when not configured or not designated; `403 operator-only` unless the session user is the configured bridge owner (`WIKI_NATIVE_MATERIALIZATION_BRIDGE_OWNER`), because shared content access is not bridge control; `409 in-progress` while another refresh of the Solution runs; `409 no-accepted-capture`; `409 stale-solution-revision`. One accepted request enqueues exactly one job with a fresh run id. Outcomes: `201 observed` (admitted), `409 unavailable` (the worker's reason, or `target-profile-bridge-failed`), `422 invalid` (the observer's errors: schema, `unattested-observation` for a foreign or replayed run id, `native-worker-revision-mismatch`, `target-mismatch`, ...), `502 unknown` (timeout or lost result) and `409 stale-solution-binding` when the Solution moved while the worker observed. Every completed attempt returns the refreshed `targetProfileRefresh`.

An admitted observation is kept in process memory only, per Solution, with the binding it was requested for: `managed.buildCapture(...).binding` = Solution id, revision, status, capture id and checksum, review-events digest and the accepted merge (artifact, revision, resolution id, result digest). It is used only while that binding is unchanged, the observer is still configured and the observation still carries its provenance mark; its age is judged by the `target-profile` gate (one day). Any other outcome of a later refresh drops it. A restart, a copy or a deserialized observation is never evidence. Nothing observes automatically: no read, page load, build or retry enqueues a job, and a lost or unknown result is not replayed.

`targetProfileRefresh` in the eligibility response is `{configured, reason, target, operator, inProgress, current, staleInputs, last: {outcome, at, reason, errors, targetProfile} | null}`. `current` means the admitted observation is used for this binding; `staleInputs` means one is held for a previous binding and ignored.

The build route's trusted evidence (`createServer` `buildEvidence`) defaults to the same source: `{observation}` admitted for the Solution's current binding. Native coverage, dependency locks and the compiler lock stay absent until the native producer supplies them (netbka/elma365#60), so the build reports `missing-native-coverage` and `missing-dependency-resolution` and never runs.

## Composer

The composer (`web/managed/composer.js`) reads the route next to the capability. «Собрать конфигурацию» stays disabled unless the builder is available **and** every gate is verified. The «Условия сборки» list shows each gate with its status and every blocking reason with a Russian label (`buildBlockReasons` in `web/managed/labels.js`); an unknown reason key stays visible with a neutral label, and more than five rows of one reason are counted. A failed eligibility read shows its own notice and keeps the build disabled. `solutionNextAction` offers `build` only under the same condition; otherwise `build-blocked`.

The «Профиль Target» group (`targetProfileView`, `targetProfileFailureView`) shows the refresh state in the same renderer: not configured, Target not designated, not yet read, reading, read for the current version (Target, platform, digest prefix, time), read for a previous version (stale inputs), unavailable, rejected report, unknown result and moved Solution, each with its reasons. «Прочитать профиль Target DEV2» is offered only to the operator with a known Solution revision; other participants see that only the bridge operator may read it. One click sends one request; a moved Solution, a running read, an unknown result or a lost response disable it until a fresh read («Обновить состояние»), and a rejected report may be retried by hand. On success the page re-reads the composer.

## Verification

`node --test test/composed-build-eligibility.test.mjs test/solution-composer-view.test.mjs` covers: absent and hand-built evidence; a diamond dependency graph planning a verified scope while synthetic coverage and receipts keep the build ineligible; a component cycle; the native path (native declaration, admitted bridge observation, native receipts) where only native installation evidence and the builder remain; a missing paid dependency, an unverified entitlement receipt and a verified licensed preinstallation; an unknown object kind; stale profiles (an observation older than a day, coverage or dependencies planned for another profile, a declaration for another profile, a resolution of another plan); order independence and immutability; today's service over a parsed capture; and the HTTP route. The composer view tests cover each gate's labels and reasons, capping, failed or malformed eligibility, the next action and every Target profile refresh state and failure. Storybook: `solution-composer--build-gates`, `solution-composer--eligibility-load-error` and `solution-composer--profile-*` (unconfigured, not operator, ready, progress, observed, stale, unavailable, invalid, unknown, moved, lost); check: `npm run test:composer:storybook`. The production page check `npm run test:composer:browser` posts exactly `{expectedRevision}` once, re-reads after success and never replays a stale or lost refresh.

`node --test test/target-profile-refresh.test.mjs` covers the refresh route over a real bridge store and an in-process synthetic HTTP worker: unconfigured and non-designated bridges, another operational actor, malformed and caller-supplied Target/bridge/report fields, a stale revision, GET without side effects, one observed `dev2` job with the server-derived payload feeding eligibility, a changed Solution making it stale, a restart dropping it, unavailable, replayed, foreign, lost and moved results never enabling the gate, and one refresh at a time. `test/composed-build.test.mjs` shows the default build evidence carrying the admitted observation while coverage and dependency evidence stay missing. All evidence is synthetic; no native build or live Target is involved, and no live dev2 observation is claimed.
