# Contextual change requests — UX-07

Authority: [intuitive Solution UI plan](../plans/intuitive-solution-ui-2026-10-15.md), section 6.7. This contract covers the persistence/API foundation and the UI built on it (`web/managed/requests.js`: entry points on processes, steps, screens, data objects and field rows, the form, the Запросы tab with records, events and publication, and `Запрос · n` chips on object rows). A request started from a uniquely declared field of a screen or data object anchors to that field (`fieldAnchor`); any other field is named in the request text and the request anchors to the object. No new worker, ELMA action or deployment authority is introduced.

## Storage and identity

Requests live in the Solution's existing private `workspace.json`, under `changeRequests`. They share its serialized atomic rename and captured-original integrity checks. All authenticated MVP actors have equal access; the trusted session supplies creation and event actors. No caller-selected storage path, actor, digest, checksum or label is trusted.

Request content is immutable: UUID, kind (`screen`, `process`, `data`), title (160 characters), desired behavior (8000), optional reason (2000), urgency (`normal`, `urgent`) and captured target. Creation requires the current Solution revision. The target selects a captured artifact in that exact Solution, optionally its component key and source step anchor. Object identity must resolve uniquely; the server copies its digest. Step identity, source pointer, fingerprint and checksum must match exactly one supported entry in the existing source-anchor index of the checksum-verified original. Unsupported or duplicate anchors fail closed. A field anchor (`fieldAnchor: {code, pointer, fingerprint}`, only with `componentKey` and never together with `sourceAnchor`) must match exactly one field that the captured screen or data object declares in the field projection of `snapshotVisual` (same code, pointer into the export and SHA-256 fingerprint of the whole declared field), and that code must be declared once in the object; a field the projection does not list (past its 200-field bound, a null slot) or a code declared twice fails closed with 409. The server stores the artifact ID and checksum, the object identity, code, pointer, fingerprint and the declared name and type copied from the checksum-verified original, never caller labels.

The UUID is an idempotency key: the original actor and exact normalized input can recover an existing creation even after the Solution changes. Changed content or actor gets 409. At most 500 requests are stored per Solution, with 200 events per request, and the serialized requests of one Solution may not exceed 4 MiB of UTF-8 (`REQUEST_STORAGE_LIMIT`); a creation or event that would cross any cap is refused with 422 and writes nothing. Missing fields in older Solution records mean no requests; reads never migrate them.

Request status is `new`, `in-progress`, `done` or `rejected`. Comments and status changes append attributed events, guarded by `expectedVersion` and a UUID `operationId`. A repeated identical operation by the same actor returns its existing result before stale checks; changed reuse fails. Concurrent edits cannot overwrite one another. Completion must name an accepted artifact in the same Solution; pending or foreign artifacts are refused. This is a person's completion assertion, not native verification. Reopening clears the fulfilling-version link and preserves history.

Reads project `anchorStatus` as current/stale/removed/ambiguous against the accepted component state, or `pending` while the target is a version still under review (not yet in the accepted artifacts): such a target is compared with nothing until that version is accepted. A component digest change conservatively makes a step or field request stale even if that step's or field's own bytes happen to be unchanged. Solution-level targets become stale after any domain revision change. The original anchor never moves to a new version. Request mutations do not advance the configuration revision, resolve review findings, accept a Change or make a candidate eligible. Archived Solutions remain readable and refuse new creation/events/publication; existing external publication receipts may still be reconciled.

## Authenticated API

All routes sit under `/api/solutions/:solutionId/change-requests`. Existing Host, Origin, service-header, authentication and JSON/body limits apply. No legacy-root ID is promoted into a Solution.

- `GET /`: `{requests, publication}`; the latter is the existing safe GitHub destination/limits configuration, never credentials.
- `POST /`: `{id, expectedRevision, kind, title, text, reason?, urgency, target: {artifactId, componentKey?, sourceAnchor? | fieldAnchor?}}`; persists locally without publication consent or external dispatch.
- `GET /:id`: the request plus its existing publication receipt or `null`.
- `POST /:id/events`: `{operationId, expectedVersion, type: 'comment', text}` or `{operationId, expectedVersion, type: 'status', status, text?, fulfilledArtifactId?}`. Comments cannot change status. Completion requires `fulfilledArtifactId`; other statuses clear it.
- `POST /:id/publish`: `{publishConfirmed: true, attachments: []}` with the existing optional image payloads. Explicit consent covers the immutable title, desired behavior, reason, kind/urgency and supplied attachments. The server constructs the report from the stored request, not caller-supplied request text or identity.
- `POST /:id/retry`: `{}`; requires an existing consented receipt and uses its immutable payload. It cannot create consent or a new report.

Publication reuses `bugReportStore`, its image checks/private downloads, repository pin, durable receipts and exact issue-marker reconciliation. Report kind is `change-request`, with the Solution/artifact/request IDs in context. The report ID is not the request ID: the server derives it from the Solution and request IDs with a per-installation secret (`bug-reports/.namespace`, claimed exclusively on first use and written whole, so concurrent first publications share one value on any filesystem), so a bug report created under a known request UUID neither blocks nor is reconciled as the request's publication. That secret is state: backups and relocations of the data directory must preserve `bug-reports/.namespace`, otherwise every published request loses its receipt, reads as unpublished and a repeated publication would open a duplicate issue. If the process dies between claiming the file and writing it, an empty `.namespace` remains and every publication fails with 500 until an operator deletes it; deleting it is safe only while nothing has been published yet. The published text names the kind and urgency in the product vocabulary (`Что изменить: Экран · Срочность: Обычная`, `Зачем: …`) and an anchored field (`Поле: Сумма · amount`), composed by `publicationText`. There is no fabricated viewport. The direct bug creation route refuses this kind: publication must resolve a real Solution request first. A UUID collision with a different report fails rather than reconciling it. Request author and publication actor remain separate facts. Authenticated identity is not added to the GitHub issue.

Local creation never publishes. The archive check precedes dispatch and runs outside the Solution queue: a Solution archived while its publication is in flight still receives the receipt, which the archived record may reconcile but not repeat. Missing GitHub configuration after consent persists `unconfigured`; failed/ambiguous dispatch retains the existing bug-report states. A lost issue response is reconciled without blind duplicate creation. Retrying after restart does not modify request content/status or accept configuration changes. An explicit publish is immutable; subsequent comments/status events are not silently republished. This slice has synthetic transport evidence only, no live GitHub publication.

Field anchors in the UI: the field rows of Экраны и данные offer the anchor when the projection lists the field with a fingerprint and its code is unique in the object; Где then reads `Поле: <name> · запрос привязан к полю`, the field stays only while Где names its object, the record and the list name it under Где, and the field row carries its own `Запрос · n` chip for open requests (the object card keeps counting them too).

Focused evidence: `node --test test/change-requests.test.mjs test/bug-reports.test.mjs test/managed-workspace-view.test.mjs`; `npm run test:managed:browser` creates a request from a step on a real server, publishes it without GitHub (`unconfigured`), comments, changes its status and sees the chip on the process card, then creates a request from a field row of a captured screen, reads its server-copied `fieldAnchor` and sees the chip on that field row only.

The synthetic HTTP correction-cycle regression also follows a field request through a changed full capture, refusal of completion against its pending artifact, acceptance, attributed completion against that exact accepted artifact, lost-response replay after restart, reopening and a later full capture that removes the object. The original field anchor and completion history remain unchanged; request events do not advance the configuration revision or publish externally. This is stored workflow evidence, not native verification of the requested correction.
