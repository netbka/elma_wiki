# Native unit and configuration-coverage adapter

Owner: #94 MR-04, PLAN-01 P4 (Wiki side). Native counterpart: netbka/elma365#60. Product authority: [Solution-first](../SOLUTION_FIRST_PRODUCT_PLAN.md) and [working configuration release](../plans/working-configuration-release.md). Implementation: `lib/native-coverage-adapter.mjs`; planner: [release-scope-planner.md](release-scope-planner.md).

`adaptNativeCoverage({request, artifacts, declarations, targetProfile, changes})` is a synchronous pure function. It admits pinned native coverage declarations, projects them into the existing `planReleaseScope` inputs (`importUnits`, `applications`, `serverInventory`), runs that planner and returns a deeply frozen record. It performs no IO, provider call, native command, materialization or Target selection; `publicationReady` and `executionEnabled` are always false. It is not wired into a store, API or UI.

## Pinned native contract: `elma365-native-coverage@1`

netbka/elma365 PR #103 (merged as `c202d6980e4bfaacf449a6b3b829b8c6580287a7`) publishes two sibling #60 contracts at **schema revision 1.1**. Wiki vendors them byte for byte with the generated capability catalog: `lib/contracts/elma365-native-coverage-1.schema.json` (sha256 `924ab59b40ebfc6fa5474148170415233193546bd79c888c212dac61a719f54d`), `lib/contracts/elma365-dependency-receipt-1.schema.json` (sha256 `788efb1e1b9eafb475c25b131d1d0ef0bbecd49c3360d117166cfd6adff89e19`) and `lib/contracts/elma365-native-coverage-1.capabilities.json`. The catalog is generated from the elma365 evidence table and moves with it: it is pinned to the merge commit of netbka/elma365 PR #104, `3d819be5cfbb24c490d323ad845da050f01d6a5e` (sha256 `f694f12d854a2755a3e78a50a509a0bd626ca8fddaad1891bc5983da438c8305`, `catalogDigest` `1f926e601b7a163ceb13609f3ba9c9f0dd281f37e8b611063109b3a4df7bb53d`). That change adds manifest policy v2 evidence and limits; no capability status changed, and both schemas are byte-identical there. Digests are over LF bytes. Revision 1.0 was an unmerged PR head and is never vendored. `lib/elma365-native-contracts.mjs` holds every pin in one place (`NATIVE_CONTRACT_SOURCE`, `COVERAGE_SOURCE`, `RECEIPT_SOURCE`, `CAPABILITY_CATALOG_SOURCE`). It validates with the E1 JSON Schema subset validator (`schemaValidator` in `lib/native-materialization-e1.mjs`) and the E1 hygiene scan, and ports the semantic rules of elma365 `tools/native-materialization/coverage.mjs` and `receipt.mjs` at that commit. A changed schema file makes `COVERAGE_SCHEMA_INTACT` or `RECEIPT_SCHEMA_INTACT` false and fails every validation as `contract-schema-drift`. A changed catalog leaves `CAPABILITY_CATALOG` null. Either way the contract is unpinned. Wiki cannot re-derive the catalog from the elma365 evidence table, so it pins the published digests instead (elma365 `validateCapabilityCatalog(..., {derive: false})`). To re-vendor a later revision, copy the three files from its merge commit and update the pins and any new semantic rules together.

`NATIVE_COVERAGE_CONTRACTS` pins exactly `{id: 'elma365-native-coverage', version: 1}` with that revision and schema digest; callers cannot extend it. A declaration under it is admitted only after `validateNativeCoverageDeclaration(doc, {catalog, captures, changes})` passes, where `captures` are the supplied artifacts of the declaration's bound Solutions and `changes` the adapter's `changes` input. Otherwise it is `invalid-native-coverage-declaration` with the elma365 reason names: schema/hygiene (`missing-field`, `unknown-field`, `invalid-value`, `host-path`, `secret-like-value`, ...), `duplicate-capture`, `duplicate-unit`, `unit-status-mismatch`, `unbound-unit-member`, `duplicate-unit-member`, `stale-target-precondition`, `stale-capability-catalog`, `stale-changes-binding`, `evidence-basis-mismatch`, `stale-capture-binding`, `uncovered-component`, `stale-member-digest`, `unknown-unit-member`, `underivable-declaration` and `capability-mismatch`. The last re-derives the classification from the pinned catalog: a declaration that claims more (or other) support or a better evidence basis than the catalog proves is rejected, as is a self-inconsistent one.

Two rules are Wiki's own obligations under 1.1:

- **Changes binding.** `changes` are the E1 operations of this release, `[{solution, key, service, kind, op, digest}]` (resulting digest, `null` for remove; `changesFromRequest(request)` builds them from a materialization request). The declaration's `changesDigest` must equal `changesDigest(changes)` recomputed here. Omitting `changes` means no changes, never skip the check. The result records `changesDigest`, and `prepareMaterializationRequest` recomputes it from its own operations.
- **Evidence basis.** Each member, unit and declaration carries `evidenceBasis` (`native-real-export`, `synthetic-fixture` or `none`). A declaration with any `synthetic-fixture` claim is admitted as **synthetic**, never native: it adds `synthetic-evidence-only` (with `evidenceBasis: 'synthetic-fixture'`) and the result's `evidenceBasis` is `synthetic`. At this catalog, widget preservation and replace are `native-real-export`; widget add/remove, `appViews`/`collection` and `permissionsSettings`/`permissionSettings` are `synthetic-fixture`.

`INSPECTED_NATIVE_CONTRACT` (status `partial`) records the facts still missing natively: `application-membership`, `part-to-unit-expansion`, `global-domain-inventory`, `global-domain-executable-handlers`, `target-preservation-policy` and `native-import-receipts`. They are schema-fixed empty/null in 1.1 (`applications: []`, `parts: []`, `server: null`, unit `receipt: null`), so application, part and full-server requests stay blocked. Every declaration under any other contract id or version returns `unknown-native-coverage-contract` and is not admitted. `SYNTHETIC_COVERAGE_CONTRACT` exists only to test Wiki accounting; any admitted synthetic declaration adds the `synthetic-evidence-only` blocker, so a synthetic result never reaches `wikiAccounting.planningComplete`.

Expected outcome with current native evidence: a widgets-only Solution plans with `evidenceBasis: native` and `wikiAccounting.evidence: planned`. It is still blocked by `unknown-target-precondition`: no observed Target profile report exists, so the declaration has no precondition. On an observed Target where the Solution is installed it is blocked by `unproven-target-preservation`, because no retain-unlisted policy is published. Even on an observed empty Target, `native-import-receipt` and `native-installation-observation` remain missing native evidence.

## Declaration document

`{contract: {id, version}, nativeRevision, adapter, evidenceRef, targetProfileDigest, captures, units, applications, parts, server}`:

- `nativeRevision` is a 40-hex native commit, with `adapter` and `evidenceRef`; otherwise `unpinned-native-declaration`.
- `targetProfileDigest` must equal `targetProfile.digest`; otherwise `stale-native-profile`.
- `captures: [{solution, artifactChecksum}]` binds the declaration to exactly one supplied capture per Solution by its `parseManagedArtifact` checksum; otherwise `stale-native-capture-binding`. A capture without a checksum is `unbound-capture`. Unit members outside the bound Solutions are `unbound-native-unit-member`.
- `units: [{id, status, evidenceRef, members: [{solution, key, digest}], unsupportedMembers?, targetPrecondition, receipt?}]` become planner import units under the declaration's adapter and profile. Member digests remain checked by the planner (`stale-native-unit-coverage`). Nonempty `unsupportedMembers` block as `unsupported-native-unit-member`.
- A nonempty Target (`mode: 'existing-target'`) additionally requires `preservation: {policy: 'retain-unlisted', evidenceRef}` and, when `targetProfile.baselineDigest` is supplied, an equal `requiredBaselineDigest`. Otherwise the precondition is withheld (`unproven-target-preservation` or `stale-target-baseline`, plus the planner's `unknown-target-precondition`).
- `applications` rows pass to the planner unchanged in shape; membership is never inferred.
- `parts: [{solution, key, componentDigest, partId, unitId}]`: a part request requires exactly one row whose `componentDigest` equals the captured component digest and whose unit contains that component; otherwise `unknown-native-part-expansion` or `stale-native-part-expansion`.
- `server: {coverage, evidenceRef, solutions, requiredGlobalDomains, domains}`. An `included` domain is projected only with `handler: {status: 'executable', evidenceRef}`; an `externally-provisioned` domain only with `verification: {status: 'verified', evidenceRef, targetProfileDigest}` on the same profile. Anything else becomes `unresolved` so the planner's global floor blocks full-server completeness, and the missing handler/verification is listed as native evidence.

Admitted declarations are merged. The same unit, component, application, part, domain or server inventory supplied by more than one declaration is `duplicate-native-provider`; no winner is chosen.

## Result

- `plan`: the unchanged planner output over the projected inputs.
- `adapterBlockers`: adapter-level blockers above.
- `wikiAccounting`: `evidence` is `planned` when declarations were admitted, else `unknown`; `planningComplete` requires both the plan and the adapter to be unblocked.
- `nativeEvidence`: facts Wiki cannot observe, kept separate from accounting: `pinned-native-coverage-contract`, per selected unit `native-import-receipt` and `native-installation-observation`, and per server domain `global-domain-executable-handler` or `global-domain-verification`. `complete` is always false here; installation observation, read-back and business acceptance remain P6/P8 native work and are named prerequisites, never synthetic success.
- `evidenceBasis`: `synthetic`, `native` or `unknown`.
- `changesDigest`: `changesDigest(changes)` of the changes native declarations were checked against.

The result is registered as produced by this module (`isNativeCoverageResult`). `prepareMaterializationRequest` and `materializeNative` accept coverage only from here, so a copy or a hand-built object claiming native or complete coverage is refused (`unverified-native-coverage`).

Catalog matching is exact on `service`/`kind`. A real Contracts export records manifest kinds such as `widget`, `template`, `permissionSettings`, `page` and `appView`, the same casing the catalog uses for its listed kinds, so nothing is case-normalized (`WIDGET` is `unknown-capability`). The real export's `appViews` kind is `appView`, while the catalog lists `appViews`/`collection`; such components stay `unknown-capability` until the native catalog lists that kind.
