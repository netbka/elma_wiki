# Contextual bug reports

Owner request: #85. Capability: `bug-reports`. Entry: a secondary side Bug icon on authenticated Wiki pages. It preserves the current page and does not introduce a primary destination or a new Solution lifecycle.

Owner decisions: Reject adds a blocking Needs changes finding to the current Solution/Change and files the bug. Attachments are published to GitHub too. Reject is available in the current Change review; elsewhere the user can file a bug and is directed to open a Change review for rejection. It does not roll back an accepted snapshot.

An authenticated actor supplies a title and description, captures a window or adds images, previews/removes attachments and optionally draws pencil marks. Up to five PNG/JPEG/WebP attachments are accepted, each at most 5 MiB. These are supported by the native GitHub media upload endpoint; PDF/text are not offered. Server enforcement is independent of the UI. Screenshots use the chosen capture source's full pixel dimensions. Capture is user initiated, uses the browser permission picker, takes one frame, and stops every track on success/error/cancellation. Cancelled or unavailable capture retains the report and offers image attachment. Annotation uses the original resolution with undo/clear/cancel/save; saved marks replace that attachment rather than consuming a sixth slot.

Before submission, the user explicitly agrees to publishing the title, description and all attachments in the named GitHub repository. Context retains only the route, viewport and supported Solution/Change IDs/revisions, not query strings or login tokens. Exact attachments also remain in private runtime storage with authenticated Wiki downloads; no screenshot is committed to Git and Wiki has no anonymous image endpoint. GitHub receives the explicitly confirmed attachments using its native user-attachment storage. All signed-in MVP actors have equal report/content access; mutation attribution comes from the trusted session. Unsupported/executable attachments are refused and Wiki downloads use attachment disposition, octet-stream and nosniff.

`BUG_REPORT_GITHUB_REPOSITORY` selects an explicit repository and `BUG_REPORT_GITHUB_TOKEN` is a server-only credential with Issues write and repository write access for native media uploads. GitHub CLI supports PAT/OAuth/user-to-server credentials for this endpoint; installation tokens are not supported. Both settings are required for publication. No existing user/GitHub login or ELMA connection is inferred. Missing configuration saves the report with `unconfigured` status, never claims a created issue, and requires an explicit later retry. Actor login is not added to the issue. Transport details follow [GitHub CLI's native attachment client](https://github.com/cli/cli/blob/trunk/internal/attachments/client.go).

## API and publication states

- `GET /api/bug-reports`: configured destination and public limits, never credentials.
- `POST /api/bug-reports`: immutable client UUID, report fields, exact attachment payload and explicit publication consent. Same actor/UUID/payload reuses the existing receipt; different content or actor is rejected.
- `GET /api/bug-reports/:id`: authenticated persisted report and attachment metadata.
- `GET /api/bug-reports/:id/attachments/:attachmentId`: authenticated, checksum-verified original/annotated attachment.
- `POST /api/bug-reports/:id/retry`: explicit retry/reconciliation of a saved report.

Reports and attachments are committed in one private staging-directory rename before domain mutation or external dispatch. Reject requires Solution ID, Change artifact ID and both domain/discussion revisions. The existing managed review operation validates identity, active state and versions, adds a `reject` event and preserves actor attribution. Report UUID is an idempotent review operation ID: the same actor/artifact/payload returns the existing finding before stale guards; changed reuse fails. A review commit followed by a lost report receipt therefore recovers without a duplicate. Unconfirmed rejection returns `blocked`, retains attachments and does not publish. The full report is retained; long review text is a bounded excerpt with a report link. Existing review resolution and acceptance gates apply. Closing a successfully rejected report refreshes the host page.

One store/process serializes submission and retries. Before issue creation it uploads every attachment, checksum-verifies its bytes and persists each GitHub asset URL. Partial upload failure returns `attachment-failed`; explicit retry retains confirmed URLs. A lost upload response can leave an orphan GitHub asset, which the UI explains; retry may upload that unconfirmed image again, but no issue has been dispatched. Publication then persists `publishing` before sending, followed by `published`, `failed` (definite HTTP refusal), or `unknown` (timeout/unreadable/ambiguous receipt). `publishing` on restart is treated as unknown. Unknown retry only reads a complete bounded issue listing and accepts one unique exact report marker; absent, duplicate or incomplete results stay unknown and never cause blind issue redispatch. The configured repository cannot silently change after upload/publication starts. This is not multi-process coordination; run one service instance per private storage directory.

The shared GitHub transport is also used by the existing request-bot adapter, preserving its private requirement projection and error contracts. Reporting does not authorize a worker, deployment, native ELMA operation or product acceptance. Synthetic Storybook fixtures use the production feedback renderer; capture and GitHub are never connected from Storybook.
