# ELMA Wiki: от возможностей к рабочему процессу разработчика

Дата решения: 2026-10-07.

Статус: продуктовый и документационный контракт из #7. Реализация #8 добавляет экспериментальный browser editor с локальной рабочей копией, TypeScript checks и операторским offline compiler/SDK profile. Tutorial и полный проверенный round trip через Wiki ещё не реализованы. Следующий этап перечислен в конце документа.

Текущие возможности и ограничения сервиса описаны в [README](../README.md) и [STATE.md](STATE.md). Загрузка приватного проекта, поиск объектов и просмотр исходного текста доступны; build, импорт и проверка текущего целевого сервера отсутствуют. Связь контрактов — в [INDEX.md](INDEX.md).

## Цель

ELMA Wiki должна отвечать не на вопрос «что находится внутри .e365», а на вопрос разработчика:

> У меня есть задача в ELMA365. Как быстрее понять, где ее решать, безопасно внести изменение и доказать результат?

Пользователь может никогда не работать с Git, ветками, commit, push, pull request и merge. Эти понятия не являются входным требованием. Wiki вводит их только тогда, когда они решают реальную задачу командной разработки.

AI-агент может пользоваться тем же маршрутом, но продукт не должен требовать AI для понимания или контроля работы.

## Продуктовый принцип

Не показывать техническую мощность раньше практической пользы.

Порядок раскрытия:

1. задача пользователя;
2. найденный объект и место изменения;
3. допустимый способ изменения;
4. проверка результата;
5. только затем техническая структура, JSON, Git и детали сборки.

Критерий готовности:

> Разработчик ELMA365, который не знает внутреннее устройство экспорта и не использует AI, самостоятельно находит нужную логику, понимает допустимый способ изменения и может проверить результат.

## Три режима работы

### 1. Разобраться быстрее, продолжая работать в Designer

Это базовый маршрут и не требует Git, терминала или AI.

Пример задачи: «Где проверяется заполнение темы обращения?»

Wiki должна:

- найти приложение, форму, поле и обнаруженные обращения;
- показать обработчик и его привязку к событию, если она доказана;
- объяснить, какие связанные объекты стоит проверить;
- дать маршрут обратно в привычный Designer.

Результат: разработчик понимает область изменения до открытия Designer.

### 2. Изменить поддержанный код в файлах

Этот маршрут показывается только для типов объектов и версий, для которых подтвержден обратный цикл.

Для проверенного widget/form сценария инструмент должен подготовить рабочие исходники, показать точный файл, проверить TypeScript и согласованность source/descriptor/runtime/history и объяснить проверку результата после импорта.

Человек не должен вручную редактировать runtime, history и служебные идентификаторы.

Если файловый round trip для объекта не подтвержден, Wiki говорит об этом прямо и возвращает пользователя к Designer. Нельзя распространять подтвержденный widget-сценарий на процессы, права, схемы или неизвестные сервисы без отдельной проверки.

### 3. Работать командой с историей и review

Git появляется после того, как у пользователя возникает задача совместной работы:

> Я хочу показать коллеге изменение, получить замечания и сохранить предыдущую версию.

Термины объясняются через результат:

- branch - отдельная линия изменения;
- commit - контрольная точка;
- push - отправка локального изменения в общий репозиторий;
- pull request - предложение проверить изменение;
- merge - принятие проверенного изменения в общую линию.

Git-репозиторий не является обязательным источником проекта Wiki. GitHub остается identity для Wiki. Командный Git-процесс - отдельный внешний workflow.

Важно: Git branch не создает отдельную компанию ELMA. Merge не публикует решение в ELMA. Успешный import exit code сам по себе не доказывает применение изменения.

## Главная страница

Первый экран должен продавать результат, а не устройство продукта.

### Основной текст

**Найдите, где менять ваше решение ELMA365.**

Загрузите .e365, разберитесь в нужной форме, поле или обработчике и получите следующий шаг: что посмотреть, где изменить и как проверить результат.

Начните с привычного Designer. Переходите к работе с файлами только там, где это действительно помогает.

Основное действие: **Загрузить E365**.

Второе действие: **Пройти пример**.

Не показывать на первом экране дерево сервисов, количество сущностей, JSON, окружения, зависимости, терминальные команды и длинный технический справочник.

## Первый экран проекта

Главный вопрос:

**Что вы хотите сделать?**

Начальные сценарии:

1. Найти нужную логику.
2. Разобраться перед изменением.
3. Подготовить проверку обновления.

Подсказки строятся по объектам именно загруженного файла. Если подходящий объект не найден или структура неизвестна, Wiki показывает границу разбора, а не синтетический сценарий как будто он применим к проекту.

## Страница «От задачи в ELMA до проверенного изменения»

Нужна отдельная иллюстрированная tutorial-страница. Она не должна быть справочником Git.

Сквозной пример:

> Форма обращения пропускает тему, состоящую из пробелов. Нужно найти проверку, исправить ее и показать результат коллеге.

### Шаг 1. Найти место изменения

Показать знакомую форму и вопрос «Где находится проверка этого поля?».

Затем показать путь:

форма -> поле -> обработчик -> привязка события -> связанные объекты.

Результат шага: пользователь может объяснить, какой объект нужно изменить и почему.

### Шаг 2. Выбрать способ работы

Два маршрута:

- **Изменить в Designer**.
- **Изменить скрипт в редакторе** - только если файловый round trip для этого объекта подтвержден.

Для неподдержанного объекта:

> Для этого типа объекта обратная загрузка пока не проверена. Используйте Designer. Найденные связи помогут проверить изменение.

### Шаг 3. Сделать изменение

Показать маленький diff «было / стало» на исходнике, который действительно редактирует человек.

Служебные производные данные отображать отдельно:

> Служебные данные для выполнения кода обновляет инструмент. Их не нужно редактировать вручную.

### Шаг 4. Проверить изменение

Проверка должна быть предметной: пустая строка, пробелы, нормальное значение.

Для файлового сценария дополнительно подтвердить, что целевая ELMA содержит ожидаемую опубликованную версию и повторный экспорт соответствует ожидаемому состоянию.

### Шаг 5. Передать на review

Только здесь объяснить branch, commit, push, pull request и merge.

Не требовать знания командной строки. Для обучения допустим GitHub web UI.

### Шаг 6. Завершить цикл

Финальная точка - работающая форма на целевой системе и понятный способ отката, а не зеленая галочка Git или exit code import.

## Структура документации

Пользовательская документация делится на четыре задачи.

### Начать

- что дает Wiki;
- загрузка одного .e365;
- учебный пример;
- первый поиск объекта.

Без установки CLI и без обязательного Git.

### Решить задачу

- найти использование поля;
- найти обработчик и его событие;
- разобраться в чужом решении;
- проверить область изменения;
- подготовить проверку обновления;
- передать изменение коллеге.

### Как мы работаем

- Designer-first;
- поддержанный file-based workflow;
- работа одному;
- работа командой;
- Git для новичка на одном сквозном примере;
- review, release и rollback.

### Справочник

- структура .e365;
- services, namespace, code;
- Context/ViewContext/RPC;
- provenance;
- версии и compatibility matrix;
- partial/unknown/opaque;
- технические ограничения.

Установка самой ELMA Wiki, Docker, OAuth и эксплуатация сервиса относятся в отдельный раздел **Администрирование Wiki**. Они не должны быть основной пользовательской документацией.

## Шаблон практической инструкции

Каждая инструкция отвечает в одинаковом порядке:

1. **Что получите**.
2. **Что потребуется**.
3. **Что сделать**.
4. **Что должно получиться**.
5. **Как проверить**.
6. **Что делать при ошибке**.
7. **Как откатить**, если операция изменяет систему.
8. **Границы применимости** - тип объекта, версии и уровень подтверждения.

## Уровни применимости

В интерфейсе нельзя использовать двусмысленное `editable` как обещание безопасной обратной загрузки.

Использовать явные состояния:

- **Просмотр** - структура читается, изменение через Wiki не подтверждено.
- **Изменение в Designer** - Wiki помогает найти объект и проверить область изменения.
- **Проверенный файловый сценарий** - round trip подтвержден для указанного типа объекта и конкретного сочетания версий. Диапазон версий допустим только при отдельном доказательстве совместимости.
- **Экспериментально** - есть исследование, но нет достаточной приемки.
- **Неизвестно** - формат не распознан или контракт не подтвержден.

Для проверенного файлового сценария всегда показывать evidence: тип объекта, версия ELMA365, версия elma365pm/tooling и способ проверки.

## Что должен взять на себя инструмент

Файловый workflow не должен означать «распакуйте JSON и разбирайтесь».

Инструмент должен:

- подготовить рабочий проект из оригинального .e365 без потери неизвестных частей;
- сопоставить понятное имя объекта с реальным архивным путем и JSON Pointer;
- отделить редактируемый source от generated/service metadata;
- для поддержанных объектов выполнять типовую проверку и генерацию производных данных;
- показывать смысловой diff поверх технического diff;
- не терять unknown/opaque части при round trip;
- проверять состояние target отдельно от provenance исходного архива;
- не хранить ELMA admin tokens в Wiki;
- не давать AI обходить проверки, которые обязательны для человека.

## Граница доказанного файлового workflow

В репозитории `netbka/elma365` есть проверенный runbook widget/form workflow и исследование compiler/import behavior.

Основание: [проверенный runbook widget/form](https://github.com/netbka/elma365/blob/d6cb44c843532be014305b04a473f0d1bef4df45/elma-development/docs/file-based-widget-dev.md). В текущих [статьях Wiki](../dist/developer-articles.js) зафиксирован скриптовый сценарий ELMA365 2026.7.23 / elma365pm 1.19.0 для установленного решения. Это внешнее испытание, а не встроенная функция Wiki. Роль целевой компании проверяется отдельно: флаг авторства в исходном архиве не доказывает возможность обновления на target.

Это не универсальный контракт всех .e365.

Публичная документация обязана:

- называть конкретные проверенные версии;
- отделять authoring solution от installed copy;
- объяснять необходимость согласованности side source, descriptor, runtime и history;
- не считать import exit 0 доказательством применения;
- проверять результат на target и повторным export;
- отдельно отмечать расхождения с официальной документацией ELMA365 и не превращать экспериментальное наблюдение в универсальное обещание.

При повторном экспорте сравнивать извлечённые исходники, descriptor, runtime и историю ожидаемых объектов. Байты двух архивов могут различаться из-за времени упаковки даже без изменения конфигурации. Неизменность сохранённого оригинала проверяется отдельно по его checksum.

## Acceptance criteria

### Пользователь без Git

1. Загружает .e365.
2. Выбирает практическую задачу.
3. Находит объект и место изменения.
4. Понимает, нужно ли идти в Designer или доступен файловый workflow.
5. Понимает, как проверить результат.
6. Ни разу не обязан разбираться в Git, JSON или Docker.

### Пользователь файлового workflow

1. Открывает поддержанный объект.
2. Получает конкретный source-файл для изменения.
3. Меняет source, не runtime/history вручную.
4. Получает понятную ошибку проверки, связанную с исходником.
5. Видит смысловой diff.
6. Выполняет update только после явного подтверждения.
7. Проверяет состояние target после update.
8. Имеет понятный rollback.

### Командный пользователь

1. Может пройти один tutorial без знания Git.
2. Понимает зачем нужны branch/commit/PR/merge до знакомства с командами.
3. Видит, что Git review и ELMA deployment - разные этапы.
4. Может объяснить коллеге, что изменилось в терминах ELMA, а не только в терминах файлов.

## Не делать

- Не превращать landing в каталог технических возможностей.
- Не требовать Git для первого полезного результата.
- Не требовать AI для файловой работы.
- Не обещать редактирование любого JSON.
- Не выдавать структурный индекс за компилятор или deploy tool.
- Не скрывать технический diff, но и не заставлять пользователя начинать с него.
- Не смешивать документацию пользователя Wiki с установкой самого сервиса.
- Не считать наличие функции доказательством ее вызова.
- Не считать source archive доказательством состояния target.
- Не считать успешный merge или import завершенной проверкой ELMA.

## Следующий этап реализации

1. Привести landing и первый экран проекта к task-first модели.
2. Создать иллюстрированную страницу «От задачи в ELMA до проверенного изменения».
3. Разделить user docs и admin docs.
4. Ввести явные уровни применимости вместо двусмысленного editable.
5. Связать инструкции с объектами конкретного загруженного проекта.
6. После этого сделать один полноценный human-first файловый workflow для уже подтвержденного widget/form сценария.
7. Только затем расширять файловое редактирование на другие типы сущностей после отдельного исследования и acceptance.
