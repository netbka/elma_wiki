# VK Teams -> GitHub -> Agent -> Dev2: план управляемой разработки

Статус: **предложено, не реализовано**. Дата: 2026-10-07.
Основание: запрос владельца спланировать полный цикл разработки через бота VK Teams и открыть PR с планом.
Базовая ревизия Wiki при подготовке: `6f821b2f1bccc9592175dfdf349ad6bbd838478b`.

Этот документ не включает подключение бота, запуск расписания, выдачу разрешений, изменение среды или деплой. Слияние документации не активирует автоматизацию и не является разрешением на выполнение будущих заявок.

## 1. Результат для пользователя

Пользователь отправляет заявку в VK Teams, отвечает на необходимые уточнения, подтверждает понятное задание и получает работающий результат: ссылку на нужную страницу Dev2, настоящий скриншот из браузера и описание выполненных проверок. Замечания возвращаются в ту же заявку. Пользователь не обязан работать в GitHub.

GitHub issue служит видимым журналом разработки; PR содержит изменения. Отдельный серверный оркестратор хранит состояние, права, подтверждения и задания исполнителям. Сам чат с ассистентом не является постоянно работающим исполнителем.

Пользовательский сценарий и тексты сообщений: [workflow](../workflows/vk-teams-agent-delivery.md). Состояния и технические ограничения определяются здесь, а не дублируются в другом контракте.

## 2. Что уже известно о проекте

- [AGENTS.md](../../AGENTS.md) требует изоляции пользовательских данных, явного Target, проверки результата развёртывания и отсутствия неподтверждённых заявлений об успехе. Эти правила сохраняются.
- [STATE.md](../STATE.md) отделяет реализованный Node-сервис от ещё не доказанного полного Source/Target runtime. Этот план не объявляет весь gateway готовым.
- [Публичный сайт](../PUBLIC_DEPLOYMENT.md) является статической сборкой. Бот, очередь, секреты, агенты и приватные скриншоты относятся к внутреннему контуру, а не к публичному Vercel.
- В [elma365/AGENTS.md](https://github.com/netbka/elma365/blob/main/AGENTS.md) DEV и Dev2 различаются; старый CLI alias `dev` указывает на Dev2. В заданиях используется зарегистрированный `target_ref`, проверенный host и идентификатор среды, а не неявный alias.
- [Файловый workflow ELMA](https://github.com/netbka/elma365/blob/main/elma-development/docs/file-based-widget-dev.md) описывает проверенные ограниченные сценарии. Их нельзя распространять на произвольные сущности, версии платформы и направления импорта.

Два типа задач нужно различать: `wiki_code` меняет код портала и развёртывает его preview; `elma_config` меняет поддерживаемую конфигурацию и импортирует её в явно выбранный ELMA Target. Публичный preview Wiki не выдаётся за проверку работающей формы в ELMA Dev2.

## 3. Архитектура первого выпуска

Предлагается внутренний Node-сервис оркестрации, PostgreSQL для состояния и надёжной очереди, отдельные изолированные исполнители и приватное хранилище артефактов. PostgreSQL — новая предлагаемая зависимость, не утверждение о текущем стеке. Redis и отдельный workflow engine для первого выпуска не требуются.

| Компонент | Ответственность |
| --- | --- |
| VK Teams adapter | Приём сообщений и кнопок, отправка вопросов, статусов, файлов; сопоставление сообщения с заявкой |
| GitHub adapter | Issues, разрешённые комментарии, ветки/PR через доверенный publisher, статусы CI и webhook-события |
| Delivery orchestrator | Проверка прав, переходы состояний, версии требований, подтверждения, очередь, лимиты и восстановление |
| Agent worker | Анализ или изменение в отдельной sandbox; структурированный результат, патч и отчёт; без прямого доступа к PROD |
| Trusted deploy/browser workers | Проверка candidate, доступ к разрешённому Target, развёртывание, read-back, браузерные сценарии и скриншоты |

Процесс не должен зависеть от одной длинной LLM-сессии. На ожидании человека worker завершается. Новый запуск получает сохранённую спецификацию, разрешения, ссылки на артефакты и проверенную ревизию репозитория. Session ID провайдера — необязательная оптимизация, а не источник истины.

Предлагаемые места реализации: `lib/delivery/`, `services/delivery-orchestrator/`, `services/delivery-worker/`, `test/delivery/`, `testing/workflows/delivery/`. Это будущие пути; данный PR их не создаёт. ELMA-адаптер оформляется отдельным согласованным PR в `elma365`, а не копированием compiler/deployer в Wiki.

## 4. Запуск по событиям и проверка каждые 15 минут

Основной режим: входящее сообщение, ответ пользователя, подтверждение, завершение агента, CI или deployment создают событие и будят оркестратор.

Для VK Teams базовый адаптер проектируется поверх long polling `events/get` с `lastEventId` и `pollTime`; поддержку webhook конкретной инсталляции нельзя предполагать. Официальный SDK содержит также отправку текста/файлов, ответы на сообщения и inline-кнопки [S1]. Точный API, лимиты и совместимость проверяются на предоставленной позднее инсталляции.

Для GitHub используются webhook-события issues/comments, PR и выбранных CI/deployment-событий. Обработчик проверяет подпись по исходным байтам, сохраняет событие и быстро отвечает; тяжёлая работа происходит из очереди [S2].

Каждые 15 минут отдельный инфраструктурный reconciler сверяет разрешённые активные заявки, состояние PR/CI/Target и потерянные lease. Это не повторная отправка всех issues в LLM и не браузерный обход GitHub. GitHub Actions cron допустим как резервный механизм, но не как точный таймер: scheduled runs могут задерживаться или пропускаться при нагрузке [S3].

Отдельно можно включить явно согласованный site-monitor: HTTP health и заданные браузерные smoke-сценарии по расписанию. Повтор одной ошибки объединяется по fingerprint в существующую заявку. Обнаружение проблемы само по себе не даёт разрешение менять код или среду. Расписание, страницы, лимит создаваемых задач и политика согласования задаются владельцем.

## 5. Состояния и переходы

```text
RECEIVED -> TRIAGING
TRIAGING -> WAITING_USER -> TRIAGING
TRIAGING -> AWAITING_SPEC_APPROVAL -> QUEUED
QUEUED -> IMPLEMENTING -> VERIFYING
VERIFYING -> IMPLEMENTING                 # ограниченное исправление ошибок
VERIFYING -> AWAITING_DEV2_APPROVAL
AWAITING_DEV2_APPROVAL -> DEPLOYING_DEV2
DEPLOYING_DEV2 -> DEPLOYED_UNVERIFIED -> VERIFYING_DEV2
VERIFYING_DEV2 -> AWAITING_ACCEPTANCE -> ACCEPTED
AWAITING_ACCEPTANCE -> CHANGES_REQUESTED -> TRIAGING
ACCEPTED -> AWAITING_MERGE -> DONE
```

`BLOCKED`, `FAILED` и `CANCELLED` — дополнительные состояния с причиной, последним безопасным checkpoint и допустимым следующим действием. `FAILED` не является «готово»; истёкшее ожидание пользователя не превращается в согласие. Возобновление выполняется только с перепроверкой актуальности разрешений, спецификации и candidate.

| Переход | Обязательное условие |
| --- | --- |
| В `QUEUED` | Согласована текущая версия спецификации; доступный бюджет; задача действительно назначена автоматизации |
| В `IMPLEMENTING` | Получен единственный lease заявки; закреплены repository/base SHA, capability и policy version |
| В `AWAITING_DEV2_APPROVAL` | Патч проверен, создан PR, обязательные проверки зелёные, candidate неизменяем и связан с проверенным SHA |
| В `DEPLOYING_DEV2` | Отдельное подтверждение конкретных candidate + Target + diff; актуальный baseline; доступен target lease |
| В `AWAITING_ACCEPTANCE` | Пройдены read-back и необходимые браузерные проверки; опубликован пакет доказательств |
| В `ACCEPTED` | Авторизованный пользователь принял конкретные spec revision + candidate + evidence; preview не устарел |
| В `DONE` | Выполнено согласованное определение готовности; для кода PR реально merged, обязательные проверки текущей итоговой ревизии подтверждены |

Бизнес-приёмка результата, техническое разрешение на merge и разрешение на PROD — разные действия. Первый выпуск не имеет PROD credentials и не предлагает кнопку PROD. Для задачи `elma_config` запись `DONE` также требует проверенного состояния Dev2 и сохранённых приватных артефактов; merge документации сам по себе её не завершает.

## 6. Анализ требований и согласование

Агент сначала читает текущие инструкции и выбранные capability-контракты, назначенную заявку и релевантный код; проверяет активные PR, чтобы не дублировать работу. Он не начинает с вопросов, ответ на которые уже есть в репозитории или истории заявки.

Уточнения нужны только для существенных пробелов: ожидаемое поведение, пользовательская роль, объект изменения, среда, данные, права, критерии приёмки. Несколько связанных вопросов отправляются одним сообщением. Для понятного запроса сразу формируется предложение задания.

Спецификация включает цель, текущую проблему, scope/non-goals, репозиторий, тип задачи, Source/Target при необходимости, проверяемые acceptance criteria, сценарии проверки, уровень риска, бюджет и предел самостоятельных исправлений. Изменение существенного требования создаёт новую `spec_revision` и аннулирует устаревшие согласования.

По умолчанию пользователь нажимает «Подтвердить задание». Позже можно разрешить документированную политику auto-start для узкого класса низкорисковых задач; это отдельное решение владельца. Агент не назначает такую политику сам.

## 7. Как сообщения связаны с GitHub

При первой валидной заявке создаются приватный request record и связанный issue через outbox. Пользователь сразу получает request ID; issue URL отправляется после подтверждения создания. Сбой GitHub оставляет состояние «заявка сохранена, синхронизация ожидается», а не ложную ссылку.

Сопоставление хранит tenant, bot identity, chat ID, sender ID, исходный message ID, request ID, issue node ID, номера PR и message IDs вопросов. Уточнение привязывается к вопросу через reply/кнопку или явный номер заявки. При нескольких активных заявках нельзя угадывать адресата ответа.

Issue — читаемый журнал и проекция утверждённой спецификации; БД — источник состояния исполнения, разрешений и lease. Метки GitHub показывают статус, но не являются единственным разрешением на запуск. При расхождении оркестратор сверяет события и аудит, а не безусловно доверяет последней метке.

Агент возвращает типизированные события: `clarification_requested`, `spec_proposed`, `progress`, `blocked`, `candidate_ready`, `evidence_ready`. Оркестратор валидирует их и создаёт сообщения/комментарии. В GitHub публикуется безопасное резюме, а не вся переписка, логи или содержимое клиентских файлов.

Разрешённые комментарии человека из GitHub также могут стать ответом или замечанием после проверки его identity/роли. Произвольный комментарий, скопированный служебный marker или сообщение другого бота не становятся командой. Собственные проекции помечаются `origin/event_id` и не возвращаются бесконечным эхом в VK Teams. CI-события разрешённых bot actors при этом не отбрасываются целиком.

В общем чате заявку создаёт явное обращение к боту или команда; обычная переписка не превращается в issues. Начальный пилот: личный диалог и список разрешённых пользователей. Возможность бота написать пользователю проверяется при onboarding; SDK указывает необходимость предварительного контакта/начала диалога [S1].

## 8. Надёжность и модель хранения

Минимальные сущности: `requests`, `spec_revisions`, `messages`, `approvals`, `runs`, `inbox_events`, `outbox_messages`, `jobs`, `candidates`, `deployments`, `evidence`, `audit_events`. Все записи owner/tenant-scoped; approval хранит actor, action, revision, candidate digest, Target, время и срок действия.

Обязательные свойства:

- Уникальный входящий ключ `(provider, tenant, bot_or_installation_id, event_id)`. Для VK сначала сохраняется вся полученная пачка в durable inbox, затем продвигается cursor. Перезапуск не должен терять ответ пользователя.
- Переход состояния и создание задания/outbox выполняются одной транзакцией. Worker получает lease с heartbeat и fencing token; старый worker после потери lease не может публиковать результат или менять Target.
- Доставка между сервисами допускает повторы. Для внешних неидемпотентных действий ведётся журнал intent/result. После неоднозначного timeout сначала ищется созданный issue/PR или проверяется Target, а не слепо повторяется операция.
- Не обещать exactly-once доставку там, где API провайдера не поддерживает idempotency. В частности, повтор уведомления возможен при потере подтверждения отправки, но не должен создавать вторую задачу или повторное согласование.
- Retry с ограничением попыток, backoff и jitter; неисправимые события попадают в dead-letter очередь с операторским статусом. API rate limits и временная недоступность не запускают бесконечный цикл LLM.
- Запоздалый результат старого run/SHA или старой версии требований сохраняется в аудит, но не двигает актуальную задачу вперёд. Edited/deleted сообщения не меняют уже утверждённые требования молча.
- Отмена прекращает выдачу новых side effects и завершает текущую безопасную стадию. Прерванный импорт получает `DEPLOYED_UNVERIFIED`/`BLOCKED` до read-back; отмена не означает автоматический откат.
- При потере/истечении cursor нельзя предполагать бесконечную историю VK: бот сообщает об обнаруженном разрыве и сверяет незакрытые вопросы. Параметры retention провайдера проверяются при подключении.

## 9. Исполнение агента и граница доверия

Первый адаптер может использовать Codex в non-interactive режиме: официально поддерживаются запуск из scripts/CI, JSONL-события и результат по JSON Schema [S4]. Контракт оркестратора остаётся независимым от провайдера; другой CLI/SDK подключается после отдельного integration test. Наличие подписки пользователя не считается автоматически настроенным серверным доступом.

Каждая задача получает отдельную sandbox/worktree и закреплённый base SHA. По умолчанию пилот запускает одного coding worker одновременно; параллелизм добавляется после проверки блокировок. Анализ выполняется read-only; изменение — с доступом только к рабочей директории. Лимиты времени, расходов, размера патча и числа циклов исправления задаются политикой; стартовое предложение — не более двух автоматических fix-циклов, затем понятная эскалация.

Код, issue-текст, вложения, комментарии, страницы и вывод команд считаются недоверенными данными. Они не могут менять policy, разрешённые Targets или список секретов. Нельзя подставлять текст пользователя в shell-команду или GitHub Actions expression без безопасного протокола аргументов.

Coding worker не получает GitHub write token, VK token, deployment credentials, Docker socket или доступ ко всей локальной машине. Доверенный publisher проверяет патч и публикует его в разрешённую ветку/PR; отдельный deploy worker принимает только проверенный candidate. Для LLM credentials использовать изолированный broker/proxy или другой поддерживаемый механизм, не отдающий ключи repo-controlled build/tests [S4].

Изменения workflow, авторизации, policy, секретов и deploy-адаптеров требуют технического ревью. Нельзя исполнять непроверенный PR-код с секретами через привилегированный workflow. Фиксируются SHA используемых Actions/runner images; workflow для привилегированных стадий берётся из доверенной ревизии. Не полагаться на неявную цепочку событий от `GITHUB_TOKEN`: оркестратор получает явное завершение/делает dispatch согласно выбранной модели [S3].

## 10. Dev2: candidate, deploy, verification

Сохраняется существующий [контракт deployment](../contracts/target-deployment.md) и [runbook](../runbooks/target-deployment.md): `draft -> checked -> ready -> deploying -> deployed-unverified -> verified`.

Для `wiki_code` candidate содержит image/build digest, source SHA и безопасные fixture references. Для `elma_config` — приватный исходный snapshot, supported workspace changes, версии compiler/platform, dependency plan, hash пакета и явный Target. Git содержит только универсальный код/документацию/синтетические fixtures, а не реальные экспорты или клиентские скрипты.

Порядок:

1. Проверить target identity, авторизацию и матрицу поддерживаемых сущностей/направлений. Зафиксировать свежий baseline и diff; изменения Designer или другого агента считаются drift.
2. Выполнить необходимые compile/lint/tests. Для ELMA — компиляция против явно выбранного host, согласованность source/runtime, поддерживаемая проверка history/version markers и полноты зависимостей. Unsupported capability останавливает задачу.
3. Создать неизменяемый candidate и показать пользователю diff, Target и риски. В первом выпуске live Dev2 deployment требует отдельного подтверждения, даже после согласования задания.
4. Получить target/solution lease, повторно сверить baseline и подтверждение. Drift требует нового candidate/review, а не автоматического force-import.
5. Применить candidate доверенным адаптером. Exit code 0 означает только завершение команды, не готовность.
6. Выполнить read-back: для Wiki сверить build identity/health; для ELMA re-export и сравнить ожидаемые сущности, source/runtime/version с учётом известных несемантических метаданных. Побайтовое равенство всего ZIP не является критерием: экспорт содержит временные метки.
7. Выполнить реальные браузерные acceptance-сценарии. Только затем разрешён статус «Готово к проверке».

Общий Dev2 нельзя бесконтрольно перезаписывать параллельными задачами. Для Wiki предпочтителен отдельный preview на PR. Для ELMA используются выделенные тестовые объекты или сериализация по Target/solution. Пока пользователь проверяет результат, действует ограниченное по времени reservation; истечение или чужой deployment делает preview устаревшим. Принятие устаревшей кнопкой отклоняется; повторный deploy/verification требует актуальных разрешений.

Rollback не равен `git revert`. Before-state и способ восстановления хранятся приватно. Для неподдерживаемого обратного перехода, миграции данных или неоднозначного импорта — остановка и оператор. При откате повторяются read-back и браузерная проверка. PROD и автоматический force-import отсутствуют в первом выпуске.

## 11. Настоящий скриншот и пакет доказательств

Playwright делает screenshot реально открытой страницы [S5]. Это не изображение, сгенерированное моделью, не Storybook вместо интегрированной страницы и не mock, выданный за Dev2.

Browser worker находится в разрешённой сети, использует тестовую учётную запись и синтетические либо явно согласованные non-production данные. Он проверяет host, deployed candidate, вход в систему и ожидаемые элементы/действия; экран логина или загрузки не считается результатом.

Пакет доказательств содержит request/spec/run IDs, candidate digest и commit SHA, target identity, deployment ID, точный page URL, UTC timestamp, viewport, список сценариев с результатами, ссылки на CI/read-back, screenshots и при необходимости trace/video. Браузерная проверка не заменяет read-back, а screenshot не заменяет проверку поведения.

Файлы хранятся приватно с проверкой доступа. В бот отправляется разрешённый screenshot как файл/изображение и доступная пользователю ссылка; в публичный issue — только безопасное резюме. Реальные клиентские данные не публикуются. Маскирование чувствительных областей должно быть явным и не скрывать проверяемую функцию. Срок хранения/удаления и TTL ссылок задаются политикой; отзыв ссылки не удаляет уже доставленное вложение из чата.

Недоступная среда, неправильная версия, падение browser test или невозможность снять screenshot дают blocker с реальной причиной, а не «готово». При изменении видимого UI в Wiki соответствующие Storybook/workflow fixtures обновляются той же задачей согласно AGENTS.md.

## 12. Права и API оркестратора

Identity сопоставляется по проверенным VK sender IDs и корпоративным/администраторским bindings, не по display name. Роли: requester, spec approver, Dev2 operator, code reviewer/merge operator, administrator. Одна персона может иметь несколько ролей; наличие в общем чате не выдаёт доступ ко всем проектам.

Кнопка содержит непрозрачный короткоживущий action token. Сервер сверяет actor, tenant, request, текущую revision, candidate, action, expiry и одноразовость. Сообщение «ок» без однозначной привязки не является разрешением на deploy.

Предлагаемые внутренние endpoints (ещё не реализованы):

- `POST /api/delivery/requests` и `GET /api/delivery/requests/:id` — создание/просмотр в своём scope.
- `POST /api/delivery/requests/:id/actions` — типизированное действие с revision и idempotency key; все права проверяются сервером.
- `POST /integrations/github/webhook` — подпись, durable inbox, быстрый ответ.
- `POST /internal/delivery/runs/:id/events` — аутентифицированный callback конкретного worker/run с fencing token; не публичный endpoint для команд.

GitHub App устанавливается только в разрешённые репозитории: metadata/contents read, issues/PR write у соответствующего адаптера; contents write только у publisher; CI/deployment read и Actions write только при реальной необходимости dispatch. Administration и доступ к secrets не нужны. До live-пилота отдельно проверяются branch rules, required checks и запрет обхода: проект не должен полагаться на то, что эти ограничения уже настроены.

Секреты хранятся в secret store/локальном bridge. Query string с token в VK API, payload с текстом и данные авторизации удаляются из proxy/access/error logs. Attachments проходят лимиты размера, проверку типа, карантин и безопасное извлечение; произвольные URL не становятся разрешёнными сетевыми целями.

## 13. План реализации отдельными PR

| Этап | Результат | Проверяемый выход |
| --- | --- | --- |
| 1. Durable core | State machine, DB/migrations, inbox/outbox, approvals, leases, fake adapters | Unit/contract tests: повторы, race, restart, stale approval/result, cancellation |
| 2. VK Teams + GitHub | Onboarding, private chat, request/issue mapping, уточнения, защищённые callbacks, webhook | Сообщение -> issue -> вопрос -> ответ без потерь, дубликатов задач и echo-loop |
| 3. Agent execution | Read-only triage, spec approval, sandbox, patch publisher, draft PR и CI feedback | Утверждённая синтетическая задача изменяет только разрешённый код; нет записи в Target |
| 4. Trusted Dev2 adapters | Wiki preview; отдельно узкий подтверждённый ELMA workflow в elma365, candidate/diff/approval, read-back | Одно согласованное изменение на выделенной non-prod цели; no-op import и drift распознаются |
| 5. Browser evidence + acceptance | Настоящие screenshots, private evidence, deep links, замечания, versioned acceptance, merge gate | Пользователь видит тот же candidate, возвращает замечание и принимает исправление |
| 6. Recovery + operations | Reconciler 15 минут, budgets, queue/runner health, dead-letter, backup/restore, operator controls | Восстановление после сбоев без повторного deploy и без потерянных заявок |

Этапы 1-3 можно разрабатывать с fake VK/ELMA adapters до получения подключений. Этап 6 начинается после этапа 1 и является обязательным условием live-пилота, а не необязательным улучшением после него. Первый вертикальный live-сценарий ограничивается одной согласованной возможностью и синтетическими данными; весь каталог ELMA не включается одним флагом.

После появления runtime добавить capability routing, контракт и runbook, обновить STATE только по наблюдаемым результатам. До этого данный документ остаётся планом. Проверки фокусируются на затронутых границах, а не заменяются формальным запуском всех тестов.

## 14. Критерии приёмки всей фичи

- Одна заявка из VK создаёт один request/issue; после перезапуска сохраняются переписка и ожидаемый вопрос. Ответ на конкретный вопрос возобновляет только свою задачу.
- Агент не пишет код до разрешённого старта и не деплоит до подтверждения актуального candidate/Target. Чужой пользователь, старая кнопка и скопированный marker не обходят ограничения.
- Ветка/PR и проверки привязаны к актуальному SHA; параллельная задача не перезаписывает чужой worktree или общий Dev2. При новом commit устаревшие evidence и approvals не принимаются.
- Пользователь получает реальный screenshot, deep link и результаты сценариев именно с проверенного candidate. Изображение ошибки/логина, stale build, no-op import и зелёная сборка без live-проверки не дают статус «готово».
- Замечания создают новую итерацию той же заявки; изменение scope требует новой версии задания. Принятие результата не включает PROD и не обходит техническое ревью PR.
- Проверены: повтор/перестановка событий, потерянный webhook, недоступность VK/GitHub/LLM/Dev2, worker crash, истёкший lease, ambiguous deploy timeout, превышенный бюджет, отмена и preview expiry.
- Ни сообщения, ни артефакты другого tenant, ни секреты, ни реальные экспорты не оказываются в Git, публичном preview или неправильном чате.

## 15. Что потребуется для подключения

Параметры владелец передаст позже из другого проекта; сейчас они не запрашиваются и не выдумываются.
