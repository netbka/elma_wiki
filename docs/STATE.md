## Implemented
- Change bases and component scope (PLAN-01 P1 / #94 MR-01; PRs #95, #103, #110): preparation accepts an optional declared base `{artifactId, revision, confirmed}` checked against the exact accepted full original (membership, checksum, acceptance revision) and pins it with snapshot/Source/scope and the trusted declaring actor in the review digest. Omitted or legacy bases stay unknown and every declaration stays `ancestryVerified: false`. Partial changes can name a captured-component scope; a base member is removed only with exact base/member evidence, and absence alone never deletes. The Solution Change form chooses a base (default "Не указывать"), requires a separate confirmation and names scope keys; review shows "Исходная версия и состав". The form sends `deletions: []` and has no deletion control. Synthetic store/API/browser tests (`test/change-base*.test.mjs`, `test/change-scope.test.mjs`, `test:change-base:browser`).
- Three-way merge plan and durable resolutions (PLAN-01 P2-P3 / #94 MR-02; PRs #107, #111): `planManagedComponentMerge` classifies each captured component of declared base B, accepted state A and incoming partial C (unchanged, one-sided, identical, divergent, addition and delete/edit classes) as clear, resolution-required or blocked; unknown base and possible renames stay blocked. `resolveManagedMerge` requires one explicit whole-component choice per conflict, a reason and a trusted actor, and records digest-bound, chained revisions in the existing workspace record (`GET/POST /api/solutions/:id/artifacts/:artifactId/merge`). Later accepted changes make a resolution stale. Saving a resolution never accepts the change. There is no byte or part-level merge, and automatic merge, acceptance and build flags stay false. The review view shows the section with four Storybook states. Synthetic tests: `test/managed-merge-*.test.mjs`, `solutions-api`, `test:merge-resolution:browser`.
